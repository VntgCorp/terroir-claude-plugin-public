# AI Gateway — 모든 AI 호출을 한곳으로 모으는 법

Terroir 안에서 AI 모델을 호출하는 요청은 모두 AI 게이트웨이 한 곳을 지납니다. 게이트웨이가 누가 호출했는지 확인하고, 어느 모델로 보낼지 정하고, 쓴 만큼 비용을 셉니다. 이 글에서는 왜 AI 호출을 한 곳으로 모았는지, 요청 한 건이 게이트웨이 안에서 어떤 순서로 처리되는지, 호출하는 쪽에서 무엇을 챙겨야 하는지를 설명합니다.

조진우 읽는 시간 약 9분

한눈에 보기 — 앱 · 사람 · CI는 모델 회사의 API 키 대신 사내 토큰을 들고 게이트웨이를 호출합니다. 게이트웨이는 신원을 확인하고, 모델을 고르고, 하루 한도를 확인하고, 프롬프트에 섞인 비밀값을 가린 뒤 Vertex AI를 호출합니다. 응답이 오면 쓴 토큰만큼 비용을 계산해 한도에 더합니다.

## AI 호출을 앱마다 따로 하면 생기는 일

앱에 AI 기능을 붙이는 가장 빠른 방법은 모델 회사의 API를 직접 호출하는 것입니다. 앱이 늘면 이 방식의 문제도 함께 늘어납니다.

왼쪽은 키가 앱 수만큼 흩어지고, 누가 얼마나 썼는지는 청구서가 와야 보입니다. 오른쪽은 앱이 사내 토큰만 들고, 확인 · 선택 · 집계 · 가림을 게이트웨이 한 곳에서 합니다.

그래서 Terroir는 AI 호출이 반드시 지나가는 관문을 하나 두었습니다. 이것을 AI 게이트웨이라고 부릅니다. 신원 확인 · 모델 선택 · 비용 집계 · 비밀값 보호를 게이트웨이가 한 번에 처리합니다. 호출하는 쪽은 요청만 보내면 됩니다.

## 어떤 도구를 골랐나

게이트웨이를 마련하는 방법은 세 가지였습니다. 셋은 프롬프트가 지나가는 길이 다릅니다.

외부 서비스는 프롬프트가 회사 밖을 지납니다. 직접 개발하면 모델 회사마다 다른 API 형식을 맞추는 일이 계속 늘어납니다. 그래서 오픈소스 agentgateway를 Terroir 클러스터에 직접 띄웠습니다.

agentgateway를 고른 이유는 두 가지입니다.

- 사내 로그인을 그대로 붙일 수 있습니다. 사내 로그인(dex) 토큰으로 호출자를 확인하는 기능이 필요했습니다. 후보 가운데 이 기능을 유료 버전이 아닌 오픈소스 버전에서 주는 것은 agentgateway 하나였습니다.
- 설정이 모두 git에 파일로 남습니다. 모델 목록이나 한도 같은 설정을 파일로 고치면, 다른 Terroir 구성처럼 클러스터에 자동으로 반영됩니다. 무엇이 언제 바뀌었는지 이력이 남고, 문제가 생기면 되돌릴 수 있습니다.

모델 공급자는 Vertex AI(Google Cloud의 모델 서비스) 하나로 두었습니다. Gemini · Claude · 공개 모델 19개를 모두 여기서 호출합니다. 게이트웨이는 API 키 없이 Vertex AI를 호출합니다. Google Cloud에 게이트웨이의 클러스터 계정을 미리 허락해 두었기 때문입니다. 그래서 사내에 보관하는 모델 회사 API 키가 하나도 없습니다. 지금은 Vertex AI만 붙어 있지만, 공급자는 더 붙일 수 있게 만들어 두었습니다. 나중에 Anthropic이나 OpenAI를 직접 붙여도 호출하는 쪽은 지금처럼 게이트웨이에 모델 이름만 적으면 됩니다.

개발자 입장에서 달라지는 점은 하나입니다. 모델 회사의 API 키를 받을 일이 없습니다. 이미 가진 사내 토큰을 그대로 들고 게이트웨이를 호출하면 됩니다.

## 요청 한 건이 지나가는 순서

게이트웨이는 요청 하나를 세 단계로 처리합니다. 먼저 어느 모델로 보낼지 정합니다. 다음으로 통과시켜도 되는 요청인지 확인하고 모델을 호출합니다. 마지막으로 응답이 오면 쓴 만큼 비용을 계산합니다.

점선 상자인 auto 판정은 "model": "auto" 로 호출한 요청만 지납니다. 모델 이름을 직접 적은 요청은 판정을 건너뛰어 기다리는 시간도 늘지 않습니다.

- 첫 단계 ‘보낼 모델 정하기’ — 모델 이름을 알아야 어느 모델로 갈지 고를 수 있으므로 이 일을 먼저 합니다. 이때 토큰을 한 번 미리 확인합니다. 토큰이 맞고 모델을 auto로 적은 요청만 auto 판정(5절에서 설명)을 거칩니다. 토큰이 틀려도 여기서 바로 돌려보내지는 않습니다. 요청 종류마다 거절하는 규칙이 달라서, 거절은 종류가 정해진 뒤인 두 번째 단계에서 합니다.
- 두 번째 단계 ‘확인하고 모델 호출하기’ — 먼저 통과시켜도 되는 요청인지 확인합니다. 토큰이 틀리면 401, 허용되지 않은 호출자면 403, 하루 한도를 이미 넘었으면 429로 끝납니다. 이때는 모델을 호출하지 않으므로 비용도 들지 않습니다. 통과한 요청은 프롬프트에 섞인 비밀값을 가린 뒤 Vertex AI의 모델을 호출합니다. 모델이 실패하면 다시 보내거나 다음 순위 모델로 넘깁니다(5절에서 설명).
- 세 번째 단계 ‘비용 계산’ — 비용은 응답이 와야 압니다. 모델이 쓴 토큰 수에 단가를 곱해야 하기 때문입니다. 그래서 두 번째 단계에서는 한도를 확인만 하고, 응답을 받은 뒤 실제 비용을 더합니다.

## 키 대신 사내 토큰으로 호출한다

게이트웨이는 자체 API 키를 발급하지 않습니다. API 키에는 만료가 없어 한 번 새면 계속 쓰이기 때문입니다. 대신 사내 로그인이나 클러스터가 서명한 토큰(JWT — 누가 언제까지 쓸 수 있는지 서명해 둔 짧은 문자열)만 받습니다. 토큰은 수명이 짧아 새더라도 금방 쓸 수 없게 됩니다.

호출하는 쪽마다 토큰을 발급하는 곳은 다르지만, 검사하는 순서는 모두 같습니다. 호출자에 따라 더 걸리는 규칙만 다릅니다.

입구는 달라도 검사는 한 길로 모입니다.

### 어디서 호출할 수 있나

이 검사는 위의 토큰 검사보다 먼저 일어납니다. 허용된 고정 주소에서 온 요청만 게이트웨이에 닿습니다. 사내 오피스와 사내 클러스터가 여기에 해당합니다. 재택에서는 사외접속 VPN을 켜도 호출할 수 없습니다. 요청이 집 인터넷 주소로 나가기 때문입니다.

## 모델을 고르는 방법은 세 가지다

요청에 적는 model 값으로 모델을 고릅니다. 적는 방법은 세 가지입니다.

- 모델 이름 — 쓸 모델을 직접 적습니다. 예를 들어 gemini-2.5-pro 라고 적으면 그 모델만 호출합니다.
- 등급 이름 — 가격대를 적습니다. chat-cheap (싼 모델) · chat-mid (중간) · chat-high (고성능) 중 하나입니다. 등급마다 모델 세 개가 순서대로 들어 있고, 앞 순위가 실패하면 다음 순위가 받습니다.
- auto — auto 라고 적으면 게이트웨이가 요청을 읽고 알맞은 모델을 골라 줍니다.

호출할 수 있는 이름은 모두 25개(모델 19 · 등급 5 · auto 1)입니다. 등급 다섯 가운데 code-review-high · code-review-mid 는 code-review-agent 전용입니다.

### 등급 이름 — 모델 세 개가 순서대로 들어 있다

| 등급 이름 | 1순위 | 2순위 | 3순위 |
| chat-cheap | gemini-3.1-flash-lite | gpt-oss-120b | grok-4.3 |
| chat-mid | gemini-3.5-flash-lite | grok-4.3 | glm-5.2 |
| chat-high | claude-sonnet-5 | grok-4.6 | gemini-3.8-flash |

순위마다 모델 회사를 다르게 둡니다. 같은 회사 모델은 공급 용량을 함께 써서 한꺼번에 거절되기 쉽기 때문입니다. 2026-10-05 기준입니다.

### 1순위가 실패하면

게이트웨이는 응답 코드만 보고 넘길지 정합니다. 답의 내용은 읽지 않습니다. 실패 횟수는 게이트웨이 서버마다 따로 세므로, 같은 이름으로 다시 보내도 다음 순위로 간다는 보장이 없습니다. code-review-agent는 그래서 code-review-high 가 실패하면 code-review-mid 로 다시 호출합니다.

### auto — 게이트웨이는 어떻게 고르나

auto로 호출하면 게이트웨이 옆의 semantic-router가 이 판정을 합니다. 언어 모델에게 묻지 않고, 다섯 신호를 점수 하나로 합쳐 등급을 고릅니다. 어느 기준에도 맞지 않으면 위 등급으로 보냅니다. 판정에는 3~5초가 더 걸립니다(개발 환경 실측 중앙값 3.6초). auto는 /v1/chat/completions 형식으로만 호출할 수 있습니다.

### 셋 중 무엇을 쓸까

auto는 요청의 마지막 user 메시지만 읽고 난이도를 매깁니다. 할 일은 system 메시지에 적고 user 메시지에는 로그나 데이터만 넣는 앱이라면, auto는 데이터만 보고 무슨 일인지 모른 채 판정합니다. 이런 앱은 auto 대신 등급 이름을 쓰세요. 등급 이름은 순위마다 모델 회사가 다릅니다(chat-high 는 Anthropic → xAI → Google). 세 모델 모두에서 답이 제대로 나오는지 먼저 확인하세요.

## 쓴 만큼 세고, 넘으면 막는다

게이트웨이는 누가 오늘 얼마나 썼는지를 금액과 토큰 수로 기록합니다. 이 기록은 게이트웨이 밖의 저장소 한 곳에 모입니다.

게이트웨이는 여러 대가 함께 떠 있습니다. 쓴 금액은 게이트웨이 밖의 카운터 한 곳(ratelimit 서비스와 Redis)에 쌓이므로, 몇 대가 떠 있어도 한도가 정확하게 지켜집니다.

### 한도를 넘기는 요청 한 건은 나간다

금액은 예시입니다. 막대는 요청이 끝난 뒤의 누적 지출입니다. 5번째 요청은 확인할 때 누적이 한도 아래라 나가고, 응답 뒤 비용이 더해져 한도를 넘습니다. 그다음 요청부터 429를 받습니다.

## 프롬프트에 섞인 비밀값은 가린다

로그나 설정 파일을 붙여 넣고 질문하면 그 안의 비밀값이 모델 회사로 함께 나갑니다. 게이트웨이는 요청이 나가기 전에 정해진 형식의 비밀값을 찾아 <masked> 로 바꿉니다.

위 프롬프트는 예시입니다. 생김새가 정해진 비밀값만 가리고, 요청을 거부하지는 않습니다. 모델의 응답에도 같은 가리기를 한 번 더 겁니다. 다만 조각으로 나눠 받는 스트리밍 응답에는 응답 쪽 가리기가 적용되지 않습니다.

정리하면, 호출하는 쪽이 할 일은 사내 토큰을 실어 보내고 모델 이름을 고르는 것뿐입니다. 신원 확인 · 한도 · 비밀값 가리기 · 비용 집계는 게이트웨이가, Vertex AI에 접속할 권한은 클러스터 계정이 맡습니다. 코드에는 모델 회사 키가 남지 않습니다.
