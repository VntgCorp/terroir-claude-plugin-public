# alert-bot · code-review-agent — 1차 확인을 맡은 두 AI 봇

Terroir에서는 알림이 오면 alert-bot이 원인과 조치를 답글로 달고, PR이 열리면 code-review-agent가 사내 규칙으로 판정을 남깁니다. 개발자가 알림이나 PR을 열었을 때는 1차 확인이 이미 끝나 있습니다. 두 봇 모두 AI 게이트웨이를 거쳐 모델을 호출합니다. 이 글에서는 두 봇이 무엇을 보고 어떤 순서로 판단하는지, 게이트웨이를 어떻게 쓰는지를 설명합니다.

## 알림과 PR이 오면 사람이 하던 일

알림이 오면 개발자는 그 시각의 로그를 찾고, 메트릭이 언제부터 달라졌는지 보고, 최근 배포를 확인한 뒤에 원인을 짐작합니다. PR이 올라오면 리뷰어는 바뀐 코드를 읽고 사내 플랫폼 표준에 맞는지 대조합니다. 둘 다 정해진 순서로 확인하는 일이라, 알림은 alert-bot에, PR은 code-review-agent에 맡겼습니다.

## alert-bot이 알림을 분석하는 순서

alert-bot은 Grafana 알림에 답글을 다는 봇입니다. 알림이 Chat 스페이스에 올라오면 같은 알림을 받아 로그 · 메트릭 · 배포 이력을 조회하고, 원인과 조치를 그 알림 스레드에 답글로 답니다.

alert-bot에서는 늘 필요한 조회를 코드가 먼저 하고, 모델은 모인 증거로 원인과 조치를 판단합니다.

Grafana는 첫 알림 카드를 Chat 스페이스에 보내면서, 같은 알림을 alert-bot에도 보냅니다(「알림 수신」). alert-bot은 해제된 알림과 5분 안에 다시 온 같은 알림을 거르고, 알림의 라벨과 설명을 보고 일곱 가지 종류 중 하나로 나눕니다(「거르기」 · 「알림 종류 나누기」). 그다음 코드가 그 종류에 정해진 증거를 먼저 조회합니다(「기본 증거」). 알림 룰의 쿼리 추이, 같은 시각의 다른 알림, 런북에 적힌 쿼리입니다.

이어서 모델이 조사합니다. 「조사 턴」에서는 조회 도구 7가지 가운데 필요한 것을 골라 호출합니다. 도구는 모두 읽기만 하고, 로그 속 비밀번호 같은 값은 가려서 모델에게 넘깁니다. 「결론 턴」에서는 도구를 끄고, 모은 결과로 원인과 조치를 정해진 형식의 답글로 씁니다.

답글은 첫 알림 카드와 같은 스레드에 카드 한 장으로 달립니다(「스레드 답글」).

「분석」에는 모델이 세 줄 요약(무슨 일 · 왜 · 할 일) 뒤에 확인된 것 · 판단 · 사람이 할 일을 적습니다.

모든 알림에 이 카드가 붙지는 않습니다. 같은 사건을 다른 알림 스레드에서 이미 분석했다면 「같은 사건」 한 줄만 남깁니다. 직전 분석 이후 증거가 같으면 다시 분석하지 않고, 「달라진 것 없음」 한 줄과 직전 결론을 남깁니다. 조회한 증거가 없으면 그 사실을 먼저 답글로 알립니다.

## code-review-agent가 PR을 판정하는 순서

code-review-agent는 PR에 판정을 남기는 봇입니다. PR이 열리거나 새 커밋이 올라오면 바뀐 코드를 사내 플랫폼 표준과 코드 품질 규칙에 비춰 판정하고, 결과를 PR에 코멘트와 check run으로 남깁니다.

code-review-agent에서는 PR에 걸리는 사내 규칙을 코드가 먼저 고르고, 모델은 그 규칙만 판정합니다.

PR이 열리거나 새 커밋이 올라오면 GitHub App이 code-review-agent에 알립니다. code-review-agent는 바뀐 파일의 경로와 줄 패턴으로 이 PR에 걸리는 규칙을 고릅니다(「규칙 고르기」). 규칙은 사내 플랫폼 표준(정합성)과 일반 코드 품질(범용 품질) 두 가지이고, 저장소 한 곳에 모여 있습니다. 걸리는 규칙이 없으면 여기서 끝나고, 있으면 리뷰할 필요가 없는 PR인지 저렴한 모델(chat-cheap )에게 먼저 묻습니다(「거르기」).

「1차 판정」에서는 코드 리뷰용 고성능 모델(code-review-high )이 규칙마다 위반인지 판정해 정해진 JSON 형식으로 답합니다. 지적마다 규칙 이름 · 심각도 · 파일과 줄 · 고칠 방법이 붙습니다. PR 제목과 설명은 지시가 아니라 참고 자료로만 모델에게 넘깁니다. 지적이 있으면 「확인」 단계가 지적한 파일 전체를 다시 읽고, 틀렸다는 근거가 나온 지적만 지웁니다.

최종 판정(approve · request_changes)은 모델의 답을 그대로 쓰지 않고, 코드가 지적의 심각도로 다시 계산합니다(「확정」). 결과는 요약 코멘트 · 줄 단위 리뷰 · check run으로 남습니다(「PR에 게시」). 머지를 막는 것은 「차단」으로 지정한 규칙의 critical 지적뿐입니다. 지금은 모든 판정을 기록만 하고 머지를 막지 않습니다.

## 어떤 방식을 골랐나

두 봇은 외부 서비스가 아니라 사내 클러스터에서 동작합니다.

- 사내 규칙과 런북을 판단 근거로 쓸 수 있습니다.
- 비용은 쓴 만큼만 듭니다. PR이나 알림 건수가 아니라 모델이 쓴 토큰 수로 정해집니다.
- 모델 회사 키가 없습니다. 게이트웨이의 신원 확인 · 비용 집계 · 비밀값 가리기가 그대로 적용됩니다.

개발자가 따로 할 일은 없습니다. 플랫폼개발팀이 팀의 알림 스페이스에 alert-bot을 붙이면 알림 스레드에 분석 답글이 달리고, code-review-agent가 적용된 저장소에서 PR을 열면 판정 코멘트가 붙습니다.

## 두 봇이 게이트웨이를 호출하는 법

| | alert-bot | code-review-agent |
| 신원 | 파드에 들어오는 토큰 파일. 호출할 때마다 다시 읽는다 |
| 쓰는 모델 이름 | 조사에 chat-high | 거르기에 chat-cheap , 판정에 code-review-high |
| auto 를 쓰지 않는 이유 | auto는 조사 도중 턴마다 모델이 바뀔 수 있다 | auto는 바뀐 코드만 보고 난이도를 매긴다 |
| 실패하면 | 그때까지 모은 결과로 결론을 쓴다 | 같은 이름으로 다시 보내고, 그래도 실패하면 code-review-mid 로 바꿔 호출한다 |

code-review-high 는 code-review-agent 전용 이름입니다. JSON 스키마로 답할 수 있는 모델만 순서대로 들어 있습니다.
