# Sealed Secrets — 비밀값을 git에 안전하게 두는 법

Terroir에 올린 앱의 DB 비밀번호와 API 키는 git 저장소에 암호화된 상태로만 기록됩니다. 원래 값은 앱이 실행되는 서버(쿠버네티스 클러스터) 안에서만 풀립니다. 이 글에서는 왜 이런 구조를 택했는지, 값이 입력된 뒤 어떤 과정을 거쳐 앱에 전달되는지를 차례로 설명합니다.

R&D실 플랫폼개발팀 읽는 시간 약 6분

한눈에 보기 — 원래 값은 git 저장소에 한 번도 기록되지 않습니다. Terroir 배포 서버가 공개키로 봉인한 값만 git에 남고, 그 값은 개인키를 가진 서버 안에서만 풀립니다.

## 비밀값은 어디에 두어야 할까

Terroir는 앱 배포에 필요한 설정을 모두 git 저장소에 기록하고, 그 내용을 서버(쿠버네티스 클러스터)에 자동으로 반영합니다(GitOps). 무엇이 언제 바뀌었는지 이력이 남고, 문제가 생기면 되돌릴 수 있습니다.

문제는 비밀값입니다. DB 비밀번호나 API 키를 그대로 적으면 git 저장소를 읽는 누구나 볼 수 있고, 나중에 지워도 git 이력에는 남습니다. 그래서 필요한 것은 git 저장소에 넣어도 안전한 형태의 비밀값입니다.

## 어떤 도구를 골랐나

| 방식 | 동작 | 결정 |
| Sealed Secrets | 공개키로 암호화한 값을 git 저장소에 두고, 서버 안의 컨트롤러가 개인키로 풀어서 쿠버네티스 Secret을 만든다 | 채택 |
| GCP Secret Manager | 값은 클라우드 금고에 두고, git 저장소에는 "어느 금고의 어느 값"인지만 적는다. 지금은 플랫폼 엔지니어용 비밀값(개인키 백업 등)에만 쓴다 | 앱용 미채택 |

Sealed Secrets를 고른 이유는 세 가지입니다.

- 외부 서비스에 기대지 않습니다.
- 앱 코드를 고치지 않아도 됩니다.
- GitOps 흐름에 그대로 들어갑니다.

개발자 입장에서 달라지는 점은 하나입니다. 암호화 도구를 설치하거나 키를 직접 다룰 일이 없습니다. 값은 포털에 넣기만 하면 되고, 봉인은 Terroir가, 복호화는 앱이 실행되는 클러스터가 맡습니다.

## 봉인은 어떻게 동작하나

Sealed Secrets는 비대칭 암호화를 씁니다. 공개키로 잠근 값은 짝이 되는 개인키로만 풀립니다. 공개키는 누구에게 공개해도 되고, 개인키는 클러스터 안의 Sealed Secrets 컨트롤러만 가지고 있습니다.

그래서 git 저장소에 들어가는 파일은 아래와 같습니다. 키 이름은 보이지만 값은 암호문입니다. 이 파일이 통째로 유출되더라도, 개인키까지 함께 새지 않는 한 원래 값을 알아낼 수 없습니다.

GitHub에 실제로 기록된 봉인 파일 — 키 이름은 보이지만 값은 모두 암호문입니다. 개발 환경 · githubmap 프로젝트 · be-api-server

서버에 이 파일이 반영되면 컨트롤러가 개인키로 값을 풀어 쿠버네티스의 일반 Secret을 만들고, 앱은 그 Secret을 환경변수로 받습니다. 앱 입장에서는 비밀값이 어떻게 저장돼 있었는지 알 필요가 없습니다.

## Terroir에서 값이 지나가는 흐름

포털 화면에 값을 넣으면 나머지는 Terroir가 처리합니다.

개발자는 포털에 값을 넣는 것까지만 하고, 봉인과 기록은 Terroir 배포 서버가 맡습니다.

값은 포털을 거쳐 Terroir 배포 서버로 전달되고, 이 서버가 앱이 배포될 환경의 공개키로 암호화해 git 저장소에 기록합니다. 원래 값은 메모리에서만 다루고 파일 · 로그 · 커밋 메시지에는 남기지 않습니다.

저장된 값은 포털에서 다시 열어도 ******** 로만 보입니다.

Terroir도 원래 값을 다시 보여 줄 수 없기 때문입니다.

포털의 환경변수 창 — 자물쇠가 켜진 항목이 Secret입니다. 저장된 값은 ******** 로만 보입니다. 개발 환경 · githubmap · be-api-server

## 암호화 말고도 막아 둔 것

포털을 거치는 값은 모두 봉인되지만, 비밀값이 유출되는 경로는 포털만이 아닙니다. 개발자가 코드나 .env 파일에 값을 적어 커밋하는 경우가 더 흔합니다. 그래서 커밋 단계에서도 비밀값을 한 번 더 걸러 냅니다. 커밋 전 검사는 비밀값 탐지 도구 gitleaks가 개발자 PC에 설치돼 있을 때만 동작합니다. 설치돼 있지 않으면 경고만 하고 넘어가므로, Terroir 개발 환경 셋팅 단계에서 함께 설치합니다.

포털 화면도 비밀값을 잘못 다루지 않도록 몇 가지를 자동으로 처리합니다.

- Secret 자동 체크 — 환경변수 이름에 PASSWORD · TOKEN · API_KEY 처럼 비밀값을 뜻하는 말이 들어 있으면 Secret 체크가 자동으로 켜집니다(대소문자 무관).
- DB 접속 정보 — DB 이름 · 사용자 · 비밀번호는 항상 Secret이고 체크를 풀 수 없습니다. 호스트 · 포트는 일반 설정입니다.
- 팀 알림 주소 — Google Chat 주소도 포털이 받는 자리에서 바로 봉인해, git 저장소에는 봉인된 값만 남습니다.
- 프론트엔드 앱은 Secret 없음 — 프론트엔드 코드는 사용자의 브라우저로 그대로 전달되어 누구나 볼 수 있습니다. 그래서 Secret 체크 대신 "입력한 값이 브라우저에 노출된다"는 경고를 띄웁니다. 비밀값이 필요한 처리는 백엔드 앱에서 하세요.

## 얼마나 안전한가

git 저장소가 통째로 유출돼도 안전하지만, GCP Secret Manager 와 같은 수준은 아닙니다. 차이는 앱이 실행되는 동안의 접근 관리에 있습니다.

| | Terroir Secret | GCP Secret Manager |
| 값을 볼 수 있는 사람 | 클러스터 관리 권한이 있는 플랫폼개발팀. 일반 사용자는 포털에서도 ******** 로만 봅니다 | 값마다 지정한 사람 · 서비스만 |
| 누가 언제 읽었는지 기록 | 없음 | 있음 |
| 버전 관리 · 자동 교체 | 없음 (새 값으로 덮어씀) | 있음 |

- 넣어도 되는 값 — DB 비밀번호, 외부 API 키, 토큰처럼 앱이 실행될 때 쓰는 일반적인 비밀값. 이 기능이 원래 맡는 일입니다.
- 먼저 상의할 값 — 접근 기록이나 주기적인 교체가 꼭 필요한 키(결제 · 개인정보 마스터키, 다른 시스템 전체 권한을 가진 키 등). 플랫폼개발팀에 문의해 주세요.

정리하면, Terroir에서 비밀값을 다룰 때 개발자가 할 일은 포털에 값을 넣고 Secret을 체크하는 것뿐입니다. 봉인과 기록은 Terroir 배포 서버가, 복호화는 앱이 실행되는 클러스터가 맡고, git 저장소에는 봉인된 값만 남습니다.

## 직접 써 보기

- Terroir 포털(terroir.vntgcorp.com)에 회사 계정으로 로그인합니다.
- 내 앱의 배포관리 화면에서 워크로드(API 서버처럼 실제로 실행되는 단위)를 열고 환경변수로 이동합니다.
- 이름과 값을 입력하고 Secret을 체크한 뒤 저장합니다. 다음 배포부터 앱이 그 값을 환경변수로 읽을 수 있습니다.

코드, .env 파일, AI 대화창에는 비밀값을 직접 적지 마세요.
