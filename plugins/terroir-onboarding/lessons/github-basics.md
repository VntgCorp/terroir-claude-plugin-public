# GitHub 처음 쓰기

Terroir로 만든 프로젝트의 파일은 GitHub라는 서비스에 보관됩니다. 이 글은 GitHub를 한 번도 써 보지 않은 분을 위해 GitHub가 무엇인지, 그리고 Terroir에서는 GitHub를 어떻게 쓰는지를 일상의 예로 설명합니다. 낱말이나 명령어를 외울 필요는 없습니다.

R&D실 플랫폼개발팀 읽는 시간 약 6분 2026-10-08 기준

01

## GitHub는 파일을 저장하고 여럿이 함께 고치는 곳입니다

GitHub는 프로젝트 파일을 인터넷에 저장해 두고, 여러 사람이 같은 파일을 함께 고칠 수 있게 해 주는 서비스입니다. 프로그램 코드만 두는 곳이 아닙니다. 기획서 · 설명 문서 · 설정 파일처럼 프로젝트에 필요한 파일이면 무엇이든 둡니다.

공유 드라이브와 비슷해 보이지만 결정적인 차이가 있습니다. 공유 드라이브에서는 누군가 파일을 덮어쓰면 이전 내용이 사라지거나 「최종_진짜최종.docx」 같은 사본이 늘어납니다. GitHub는 바뀐 내용을 하나하나 기록으로 남기고, 다른 사람이 고친 것을 확인한 뒤에 합치는 절차를 갖고 있습니다. 이 두 가지가 이 글의 중심입니다.

02

## 저장소에는 누가 언제 무엇을 바꿨는지 기록이 남습니다

저장소(레포지토리, 줄여서 레포)는 프로젝트 하나의 파일을 담는 폴더입니다. 보통 프로젝트 하나에 저장소 하나를 둡니다. 일반 폴더와 다른 점은 파일과 함께 바뀐 기록 전체를 담고 있다는 것입니다.

파일을 고친 뒤 「이만큼 고쳤다」 하고 기록으로 남기는 것을 커밋(commit)이라고 합니다. 게임의 저장 버튼에 메모를 붙이는 것과 비슷합니다. 커밋 하나에는 누가 · 언제 · 어떤 파일의 어느 줄을 · 왜 바꿨는지가 남습니다. 「왜」는 커밋할 때 적는 짧은 설명(커밋 메시지)입니다.

커밋 기록 — 점 하나가 커밋 하나입니다. 기록이 쌓여 있으므로 「버튼 색은 누가 언제 바꿨지?」를 사람에게 묻지 않고 저장소에서 바로 찾을 수 있고, 필요하면 이전 상태로 되돌릴 수도 있습니다.

커밋은 처음에는 내 컴퓨터에만 남습니다. 내 컴퓨터의 커밋을 GitHub 저장소로 올리는 것을 push(푸시)라고 합니다. 다 쓴 메일도 보내기를 눌러야 상대가 받는 것처럼, 올려야 다른 사람도 볼 수 있습니다.

03

## 바꾼 것은 PR로 요청하고, 확인을 거쳐 합칩니다

여럿이 같은 파일을 동시에 고치면 서로의 작업이 엉킵니다. 그래서 원본은 그대로 두고, 원본에서 갈라져 나온 작업 공간인 브랜치(branch, 나뭇가지)에서 고칩니다. 문서 원본 대신 사본을 만들어 고쳐 보는 것과 비슷합니다. 원본 역할을 하는 브랜치는 보통 main , develop 같은 이름을 갖습니다.

브랜치에서 고친 것을 원본에 넣으려면 「이렇게 바꿔도 될까요?」 하고 요청을 올립니다. 이 요청이 PR(Pull Request)입니다. 회사에서 결재를 올리는 것과 비슷합니다. PR 화면에는 무엇이 바뀌었는지가 줄 단위로 보이고, 동료는 그 화면에서 의견을 남길 수 있습니다. 확인이 끝나 원본에 합치는 것을 머지(merge)라고 합니다.

한눈에 보기 — 바꾼 것이 원본에 들어가는 길입니다. 고친 사람이 바로 원본을 바꾸지 않고, PR이라는 요청을 거쳐 합칩니다.

PR은 머지한 뒤에도 사라지지 않습니다. 그래서 나중에 PR 기록을 열어 보면 누가 어떤 코드를 넣었고, 누가 확인해 합쳤는지를 알 수 있습니다.

04

## GitHub Actions는 정해 둔 검사와 빌드를 저절로 돌립니다

GitHub Actions는 미리 적어 둔 작업을 정해진 때에 저절로 실행하는 GitHub 기능입니다. 「PR이 올라오면 검사한다」, 「머지되면 앱을 만든다」 같은 식입니다.

여기서 빌드는 고친 코드를 실제로 실행할 수 있는 묶음으로 만드는 일입니다. 손질한 재료를 바로 먹을 수 있는 도시락으로 싸 두는 것과 비슷합니다.

진행 상황은 저장소의 Actions 탭에서 볼 수 있습니다. 초록불이면 성공입니다. 빨간불이면 실패한 작업을 열어 가장 먼저 빨갛게 표시된 단계의 기록을 확인하고, 고친 뒤 다시 실행합니다.

05

## Terroir에서는 GitHub를 이렇게 씁니다

지금까지 본 것은 어느 GitHub 저장소에나 해당합니다. Terroir로 만든 저장소에는 여기에 몇 가지가 미리 정해져 있습니다.

### 원본은 PR로만 바꿀 수 있습니다

Terroir로 저장소를 만들면 원본 브랜치인 main 과 develop 에 보호 규칙이 자동으로 걸립니다. 원본 서류함에 자물쇠를 채워 결재를 거친 것만 넣게 한 것과 같습니다. 이 두 브랜치에는 push로 직접 올릴 수 없고 반드시 PR을 거쳐 머지해야 합니다. 저장소 관리자도 예외가 없습니다.

main · develop 보호 규칙 Terroir로 만든 저장소에 자동 적용

PR로만 반영직접 push는 막힘

강제 push · 브랜치 삭제 금지기록을 덮어쓰거나 지울 수 없음

관리자도 예외 없음누구든 PR을 거침

승인 수 0 · 필수 검사 없음혼자서도 머지할 수 있음

강제 push는 저장소에 있는 기록을 내 컴퓨터의 기록으로 덮어쓰는 것입니다. 실수로 하면 남의 작업이 사라질 수 있어 막아 둡니다.

승인은 동료가 바뀐 내용을 읽고 「괜찮다」고 표시하는 것이고, 필수 검사는 자동 검사를 통과해야만 머지할 수 있게 하는 설정입니다. 둘 다 처음에는 걸려 있지 않아, 다른 사람의 승인 없이도 머지할 수 있습니다. 이 규칙의 목적이 확인을 강제하는 것이 아니라 실수를 막는 것이기 때문입니다. 혼자 운영하는 저장소도 머지할 수 있어야 합니다.

작업용 브랜치는 feature/… 로 시작하는 이름으로 만들고, develop 으로 PR을 올립니다. 이름이나 방향이 정해진 흐름에 맞지 않으면 PR 검사(브랜치 흐름)가 실패합니다.

### 첫 PR부터 시작합니다

Terroir 포털에서 새 프로젝트를 만들면 GitHub에 저장소가 생기고, 앱의 기본 코드가 담긴 첫 PR이 열립니다. 이때 코드는 아직 원본에 들어가지 않았습니다. 첫 PR을 머지해야 코드가 develop 에 들어가고, 그 순간 자동 작업이 돌기 시작합니다.

포털 프로젝트 만들기 종류를 고르고 이름을 정해 생성

첫 PR이 열린다 ──▶

GitHub 첫 PR 머지 Merge pull request(합치기) 버튼을 누른다

코드가 develop에 ──▶

내 컴퓨터 clone 저장소를 기록째 내려받는다

그다음부터 ──▶

내 컴퓨터 고치고 PR 작업 브랜치에서 고쳐 develop으로 PR

Terroir 프로젝트의 시작 — 첫 PR을 머지한 뒤 내려받아, 그 코드를 고쳐 나갑니다.

첫 PR은 포털 결과 화면의 링크로 열거나 저장소의 Pull requests 탭에서 찾습니다. PR에 정해진 합칠 대상 브랜치는 바꾸지 말고 그대로 머지합니다. 바꾸면 코드가 들어가지 않습니다.

머지한 뒤 저장소를 내 컴퓨터로 내려받는 것을 clone(클론, 복제)이라고 합니다. 공유 폴더를 통째로 복사해 오는 것과 비슷하지만, 파일만이 아니라 지금까지의 커밋 기록까지 함께 받습니다. 그 뒤로는 고치고, 커밋하고, push하고, PR을 올려 머지하는 일이 반복됩니다.

### 합치면 검사 · 빌드 · 배포로 이어집니다

Terroir로 만든 저장소에는 04 절의 GitHub Actions 작업이 처음부터 들어 있습니다. PR을 열면 검사가, 머지하면 빌드가 저절로 돕니다.

PR을 열면 자동 검사 코드 규칙 · 빌드 · 테스트 등 다섯 가지를 확인한다

머지 ──▶

머지하면 빌드 바뀐 앱만 골라 실행할 수 있는 묶음(이미지)을 만든다

언제든 ──▶

Actions 탭 진행 상황 보기 초록불은 성공, 빨간불이면 실패한 단계의 기록을 연다

Terroir 저장소의 자동 작업 — PR 단계에서는 검사가, 머지 뒤에는 빌드가 돕니다.

필수 검사가 걸려 있지 않으므로 검사가 실패해도 머지할 수는 있습니다. 다만 실패를 무시하고 합쳤다는 기록이 PR에 남습니다.

배포는 만든 앱을 서버에 올려 다른 사람이 쓸 수 있게 하는 일입니다. Terroir 포털(Terroir의 웹 관리 화면)에서 배포를 한 번 설정해 둔 프로젝트는 그다음부터 develop 에 머지하는 것만으로 빌드부터 서버 반영까지 이어집니다. 즉 머지는 배포를 시작하는 계기입니다. 배포 기록은 PR이 아니라 배포를 맡은 도구 쪽에 따로 남습니다.

### 포털에는 회사 GitHub 계정으로 로그인합니다

GitHub의 조직(organization)은 회사 이름으로 묶인 공간입니다. 회사 저장소는 이 조직 아래에 있고(github.com/VntgCorp/… ), 조직 안에는 회사 안의 부서처럼 다시 팀이 있습니다.

포털에는 회사 GitHub 조직에 속한 계정으로 로그인합니다. 회사 Google 계정으로는 조회만 할 수 있습니다. 배포, 배포 되돌리기(롤백), 앱 설정값(환경변수) 바꾸기 같은 작업은 그 프로젝트를 맡은 GitHub 팀에 속한 사람만 할 수 있습니다. 포털이 GitHub 팀을 그대로 포털의 그룹으로 쓰기 때문입니다.

### 기획서도 PR로 넘어갑니다

GitHub는 개발자만 쓰는 곳이 아닙니다. Terroir의 기획 · 디자인 AI로 기획서를 만들면, 기획서는 저장소의 정해진 자리에 자동으로 놓이고 PR로 개발에 넘어갑니다. 디자인 시안은 디자인 도구(Claude Design)에 두고, 그 링크를 기획서와 함께 PR로 넘깁니다.

기획서와 시안을 따로 전달하고 회의로 설명하지 않아도, 개발자는 저장소에서 바로 찾아보고 언제 무엇이 바뀌었는지 기록으로 확인합니다. GitHub 계정이 없는 사람도 포털에서 기획서를 읽을 수 있습니다.

06

## 한 번에 정리

| 낱말 | 뜻 | 비슷한 일상의 예 |
| 저장소 (레포) | 프로젝트 하나의 파일과 바뀐 기록 전체를 담는 곳 | 변경 이력이 붙은 프로젝트 폴더 |
| 커밋 | 고친 내용을 누가 · 언제 · 왜와 함께 기록으로 남기는 것 | 메모를 붙인 저장 버튼 |
| push · clone | 내 기록을 GitHub로 올리기 · 저장소를 기록째 내려받기 | 메일 보내기 · 공유 폴더 통째로 복사 |
| 브랜치 | 원본을 그대로 두고 따로 고치는 작업 공간 | 원본 대신 사본에 고쳐 보기 |
| PR · 머지 | 「이렇게 바꿔도 될까요?」 요청 · 확인 뒤 원본에 합치기 | 결재 올리기 · 결재 뒤 반영 |
| GitHub Actions | PR · 머지 같은 때에 검사와 빌드를 자동으로 돌리는 기능 | 「PR이 올라오면 검사한다」 같은 약속 |
| 보호 규칙 | 원본 브랜치를 PR로만 바꿀 수 있게 잠가 두는 설정 | 결재를 거친 것만 넣는 서류함 |

Terroir에서 가장 먼저 손에 익힐 것은 PR과 머지입니다. 보호 규칙이 실수를 막고, 검사와 빌드는 자동으로 돌고, 누가 어떤 코드를 넣고 누가 합쳤는지는 PR에 남습니다.
