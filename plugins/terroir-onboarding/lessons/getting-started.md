도구를 하나씩 직접 설치할 필요는 없습니다. Claude Code 에서 아래를 차례로 입력하면 무엇이 필요한지 확인해서 설치와 연결까지 해 줍니다. 이미 했다면 건너뛰세요.


✓

선택 Windows 에서 작업한다면
WSL2 가 필요하고, 코드는 반드시 WSL 홈(`~/`) 아래에 둬야 합니다.

`/mnt/c/...` 아래에서 작업하면 빌드가 5~10배 느려지고, hot reload 가 멈추고, 파일 권한과 심볼릭 링크가 깨집니다. `~/workspace/...` 처럼 WSL 홈 안에 내려받으세요.

## GitHub 02 머지하고 내려받기

앱 코드(`apps` · `libs` · `terroir.json`)는 첫 PR 안에 있습니다. 01 결과 화면의 첫 PR 링크를 눌러 GitHub 으로 가서 Merge pull request 를 누르세요. 머지해야 코드가 `develop` 에 들어가고, 그 순간 CI 가 돌기 시작합니다. base 브랜치는 PR 에 설정된 그대로 두세요 — 바꾸면 코드가 들어가지 않고 배포 탭도 열리지 않습니다.

결과 화면을 이미 닫았다면 레포의 Pull requests 탭에 열려 있는 PR 하나가 그것입니다. 레포 이름이 기억나지 않으면 포털 왼쪽 내 프로젝트 목록에서 찾습니다.

<레포이름> 은 본인 것으로

```
# 첫 PR 을 머지한 뒤에
git clone https://github.com/VntgCorp/<레포이름>.git
cd <레포이름>
git checkout develop
./setup.sh   # pnpm 준비 · install · git hook 설치
```

✓
`ls` 를 실행했을 때 `apps/` · `Makefile` · `terroir.json` 이 보이면 됩니다. 안 보이면 머지가 안 됐거나 다른 브랜치입니다. DB 를 쓸 앱이면 여기서 05 로 한 번 다녀오세요.

참고 레포 안에 뭐가 들어 있나
파일은 managed(플랫폼이 계속 관리 · 고치면 덮어써짐)와 once(최초 1회만 설치 · 내 자산) 둘로 나뉩니다.

```
apps/                # 애플리케이션 — 샘플 앱이 들어 있다
libs/                # 내 프로젝트 공유 라이브러리
infra/local/docker/  # 로컬 인프라 (Postgres · Redis · Kafka …)
docs/                # 내 프로젝트 문서
terroir/             # 플랫폼 영역 — 직접 고치지 않는다
.github/workflows/   # PR 체크 · 배포 파이프라인
terroir.json         # 배포 매니페스트 — CI 와 포털이 읽는다
Makefile             # 기동 진입점
```

파일 상단 주석에 managed 인지 once 인지 적혀 있습니다. managed(워크플로 · lint 설정 · `terroir/`)는 플랫폼팀이 계속 관리해서 부트스트랩 업데이트 때 덮어씁니다 — 고쳐도 다음 업데이트 때 사라집니다. once(`package.json` · 앱 코드 · `docs/`)는 처음 한 번만 설치되고 그 뒤로는 내 파일이라 마음대로 고쳐도 됩니다.

## 로컬 03 로컬에서 확인

컨테이너 런타임이 켜져 있어야 합니다(00 에서 깐 것). 꺼져 있으면 `make all-up` 이 실패합니다.

`make all-up` 은 로컬 DB 도 함께 띄웁니다. DB 를 쓰는 샘플 `be-api-server` 가 붙지 못하면 레포 루트 `.env` 의 `DATABASE_URL` 이 주석 처리된 채로 있는지 확인하세요 — 이 값은 로컬 전용이고 배포 환경에서는 쓰지 않습니다.

```
make all-up     # 인프라 + 앱 한 번에
make all-down   # 정지
```

```
🌐 API Server:     http://localhost:43000
🌐 DBless Server:  http://localhost:43100
🌐 User Client:    http://localhost:45173
```

✓
이렇게 세 줄이 출력되고 브라우저로 열었을 때 화면이 나오면 성공입니다. 그 포트가 이미 쓰이고 있으면 비어 있는 다음 포트로 자동으로 옮겨 가니, 숫자를 외우지 말고 출력된 주소를 그대로 여세요.

참고 따로 띄우기 · AI 에이전트로 띄우기
인프라와 앱을 나눠 올릴 수 있고, Claude Code 에 「가동시켜」 라고 해도 됩니다.

```
make infra-up   # Postgres · Redis · Kafka · 관측성만
make app-up     # 앱 컨테이너만 (hot reload)
make all-up     # 위 둘을 한 번에
```

레포 루트에서 Claude Code 를 켜고 「가동시켜」 라고 해도 됩니다. 실패했을 때 원인까지 함께 찾아 줍니다.

반드시 레포 루트에서 켜세요
`.claude/` 는 세션을 시작한 디렉터리에서만 읽힙니다. `cd apps/api && claude` 처럼 하위에서 켜면 가드레일이 전혀 적용되지 않습니다. 특정 앱만 만질 때도 루트에서 켜고 경로로 지정하세요.

## GitHub 04 빌드 확인

02 에서 머지하는 순간 CI 가 돌기 시작했습니다. 레포의 Actions 탭에서 진행을 볼 수 있고, 몇 분 뒤 이미지가 만들어집니다. 여기서는 따로 할 일이 없습니다 — 끝나기를 기다리면 됩니다.

빨간불이면 실패한 job 을 열어 가장 먼저 빨간 스텝의 로그를 확인합니다. 고친 뒤 Re-run jobs 로 다시 실행합니다.

초록불을 믿지 마세요
초록이어도 「건너뛰었다」일 수 있습니다. 판정 기준은 머지 대상(base) 브랜치인데, 그 브랜치가 `terroir.json` 의 `environments` 에 없으면 아무것도 만들지 않고 성공으로 끝납니다.

✓
Actions 탭에서 초록으로 끝나면 됩니다. 무엇이 실제로 배포됐는지는 06 에서 워크로드를 등록한 뒤 배포 탭에서 확인합니다 — 지금 배포 탭이 비어 있는 것은 정상입니다.

참고 코드를 고쳐서 다시 올리려면
작업은 `feature/*` 에서 하고 `develop` 으로 PR 을 올려 머지합니다. 머지해야 배포가 시작됩니다.

```
git checkout -b feature/add-user-auth
# 코드를 고친 뒤
git commit -am "feat(auth): add login endpoint"   # scope 필수
git push -u origin feature/add-user-auth
```

푸시하면 터미널에 PR 생성 링크가 뜹니다. 그 링크로 들어가 base 를 `develop` 으로 두고 PR 을 만든 뒤 머지하면 됩니다. `gh pr create --base develop` 로 만들어도 같습니다.

커밋 메시지는 `type(scope): subject` 형식이고 scope 가 필수라, 형식이 틀리면 커밋 자체가 막힙니다.

## 포털 05 DB 연동 [DB 를 쓴다면]

DB 를 안 쓰는 앱이면 건너뛰세요. 다만 포털이 만들어 준 샘플 앱 중 `be-api-server` 는 DB 를 쓰므로, 샘플을 그대로 실행해 볼 생각이면 이 단계가 필요합니다. (`be-dbless-server` 는 DB 없이도 동작합니다.)

### 1. 신청하고 기다립니다

포털 프로젝트 화면 → ＋ DB 추가. 폼 한 장을 내면 끝이지만, 내는 순간 생기지는 않습니다. 신청은 인프라 저장소의 PR 로 올라가고, 플랫폼개발팀이 그 PR 을 머지해야 실제로 발급됩니다. 그래서 06 에 도달하기 전에 미리 내 두는 편이 좋습니다.

신청부터 쓸 수 있게 되기까지

- 폼을 낸다 — 아래 네 칸을 채우고 제출합니다.
- 기다린다 — 플랫폼개발팀이 인프라 저장소의 PR 을 머지합니다. 여기는 내가 할 일이 없습니다.
- 발급된다 — 접속 정보 세 개가 06 환경변수의 「추가 항목」에 저절로 들어옵니다.

폼에서 채울 것은 넷입니다.

- 발급 환경 — 개발 (dev). 환경당 하나씩만 만들 수 있습니다.
- DB 이름 — 뒤에 올 이름만 적습니다. 앞에 프로젝트 이름이 자동으로 붙습니다.
- 접속할 사용자 계정(필수) — 스키마 변경을 직접 할 사람의 조직 Google 계정(`@vntgcorp.com`)을 소문자로 적습니다. 여러 명을 적어도 됩니다. 여기서 같이 신청해 두는 편이 훨씬 빠릅니다 — 나중에 따로 신청하면 절차가 더 깁니다.
- 접속할 워크로드 — 여기서 앱이 DB 에 붙습니다. `terroir.json` 에 적힌 이름(예: `be-api-server`)을 고릅니다.

「프로젝트」 는 이미 채워져 있고, 「이 DB 를 사용할 애플리케이션」 은 화면에 같이 보이게 하는 표시용이라 비워 둬도 됩니다.

### 2. 발급되면 — 고칠 코드가 없습니다

루트 모듈이 `PrismaModule` 을 import 하고 있다면 고칠 코드가 없습니다. 접속 정보 세 개가 06 환경변수의 「추가 항목」에 들어갑니다. 배포 환경에서는 IAM 인증이라 비밀번호가 없습니다 — 값을 손으로 채우거나 `DATABASE_URL` 에 접속 정보를 적지 마세요. (로컬의 `.env` 는 그대로 써도 됩니다. 로컬과 배포 환경은 별개입니다.)

```
CLOUD_SQL_INSTANCE    # 이 값이 있으면 배포 경로, 없으면 로컬 경로
CLOUD_SQL_IAM_USER
CLOUD_SQL_DATABASE
```

✓
06 환경변수 화면을 열었을 때 이 세 키가 «추가됨» 으로 보이면 연결된 것입니다. 안 보이면 아직 발급·연결 전이니 플랫폼개발팀에 문의하세요.

| 사무실(사내망) | 없습니다. 사내망이 그대로 닿습니다 |
| 재택 · 외근 | 사외접속 VPN 이 전제입니다. 전자결재로 신청·접수·설치·2차 인증을 거치므로 접속 테스트보다 먼저 해 두세요 |

비밀번호는 없습니다. `gcloud auth print-access-token` 으로 받은 토큰이 비밀번호 자리에 들어가고 1시간 뒤 만료됩니다. 신원은 본인 조직 Google 계정이고, 그 계정이 DB 에 등록돼 있어야 합니다 — 05 신청의 「접속할 사용자 계정」 이 바로 그것입니다.

접속 스크립트는 레포 안 `terroir/docs/data/cloud-sql-local-access/` 에 있습니다.

```
# 1) 진단 — 어디가 막혔는지 먼저 본다 (조회만)
./check-access.sh --db <논리DB이름>

# 2) 접속 — 진단이 통과하면
./connect.sh --db <논리DB이름> --user <본인계정>@vntgcorp.com
```

`--db` 를 꼭 붙이세요. 없이 돌리면 로그인·클라이언트 검사를 건너뛰어서 「막힌 곳 없음」이라고 나온 뒤 2)에서 실패합니다.

#### 정말 붙었는지

기동 로그나 「연결 성공」은 증거가 아닙니다. 쿼리를 한 번 실행해 봐야 확인됩니다.

```
SELECT current_database()::text AS database,
       current_user::text AS "user"
```

`user` 가 `<프로젝트>@….iam` 형태이고 `database` 가 발급받은 이름이면 의도한 계정으로 의도한 DB 에 접속된 것입니다. `::text` 를 빼면 ORM 이 역직렬화에 실패하니 그대로 쓰세요.

#### 스키마 반영(마이그레이션)

Prisma 마이그레이션 명령을 돌리지 마세요
이 인스턴스에 `prisma migrate dev` · `migrate deploy` · `db push` 를 실행하면 안 됩니다. 공용 dev 논리 DB 는 같은 프로젝트 사람들이 함께 씁니다 — 내 로컬에서 나간 DDL 을 다 같이 맞습니다. 기동할 때 마이그레이션을 자동으로 도는 앱이라면 그것부터 떼고 붙이세요.

DDL 반영 경로는 아직 정리 중입니다. 예전 문서의 「DBeaver + VPN 으로 직접 실행」은 비밀번호 없는 IAM 인증을 쓰는 지금 인스턴스에 그대로 적용되지 않습니다. 스키마를 바꿔야 하면 플랫폼개발팀에 문의하세요.

참고 공용 DB 말고 다른 방법
클러스터에 직접 띄우거나, 이미 있는 외부 DB 를 그대로 쓰는 길도 있습니다. 둘 다 신규 프로젝트에는 권장하지 않습니다.

| 방법 | 할 일 |
| 클러스터 안 DB | `terroir.json` 의 `workloads` 에 `type: "DB"` 와 `engine: "postgres"` 를 선언합니다. 이 선언을 읽는 것은 06 의 워크로드 등록 화면이므로 06 에 가기 전에 배포 브랜치에 들어가 있으면 됩니다. 디스크는 20Gi 고정입니다. 표준 문서는 신규 프로젝트에 권장하지 않습니다 |
| 이미 있는 외부 DB | `terroir.json` 에는 선언하지 않고, 06 환경변수의 Secret 에 접속 정보를 직접 넣습니다 |

접속 규약의 원본 문서는 레포 안 `terroir/docs/data/cloud-sql-connection.md` 입니다.

## 포털 06 배포 등록하고 설정

워크로드는 따로 빌드해서 따로 실행하는 단위입니다 — 서버 하나, 프론트 하나. `terroir.json` 에 적힌 워크로드마다 배포 탭에 카드가 하나씩 생기고, 카드의 배지가 그 워크로드의 현재 상태를 나타냅니다.

프로젝트 → 애플리케이션 → 배포(개발) 탭. 탭은 환경마다 하나씩 있습니다. 오른쪽 위 ＋ 워크로드 등록 을 누르면 포털이 `terroir.json` 을 읽어 워크로드를 가져옵니다.

✓
워크로드 카드가 생기고 배지가 «환경설정 필요» 로 보이면 등록이 끝난 것입니다.

### 카드마다 세 칸을 모두 채웁니다

등록하면 `terroir.json` 에 적힌 워크로드마다 카드가 하나씩 생깁니다. 샘플 그대로라면 `be-api-server` · `be-dbless-server` · `fe-user-client` 셋입니다.

카드마다 리소스 · 접속 설정 · 환경변수 버튼이 있고, 각각 별도 화면으로 열립니다. 버튼에 붙은 점이 아직 안 채웠다는 표시입니다 — 셋을 모두 채워야 배지가 «배포 대기» 로 바뀝니다.

위에서 아래 순서로 채우세요. 순서를 건너뛰면 저장이 막힙니다.

| 화면 | 칸 | 할 일 |
| 리소스 | — | 프리셋 그대로 두고 저장만 누릅니다. 눌러야 미완료 점이 사라집니다 |
| 접속 설정 | `containerPort` | 앱이 컨테이너 안에서 쓰는 포트입니다. 샘플은 `be-api-server` 43000 · `be-dbless-server` 43100 · `fe-user-client` 80. FE 는 `45173` 이 아니라 `80` 입니다. 비워 두면 저장이 안 됩니다 |
| `livenessProbe path` | 이 경로가 응답하지 않으면 앱이 자동으로 재시작됩니다. 기본값(BE `/api/health` · FE `/health`)이 내 앱에 실제로 있는지 확인하세요 |
| 노출 | 사내망과 인터넷 두 줄이 따로 있고 둘 다 기본이 «비노출» 입니다. 브라우저로 열어 볼 워크로드(보통 `fe-user-client`)는 사내망만 켜면 됩니다 |
| 환경변수 | 필수 항목 | 모두 채워 «설정됨» 으로 만듭니다. 자물쇠가 파란 칸은 비밀값이라 화면에 보이지 않습니다 |
| 주소가 들어가는 칸 | `.env 붙여넣기` 는 쓰지 마세요 — 로컬 값은 `localhost` 라 배포 환경에서는 접속되지 않습니다. 값 오른쪽 🔗 를 눌러 다른 워크로드를 고르면 됩니다 |

프론트엔드는 저장 버튼이 꺼져 있습니다. 환경변수가 빌드할 때 코드에 포함되기 때문입니다. 값을 다 채운 뒤 화면 아래 [배포] 자리에 뜨는 「빌드 시작」 을 누르면 저장과 빌드를 함께 처리합니다.

노출은 켜면 되돌릴 수 없습니다
한 번 노출한 채널은 «비노출» 로 되돌릴 수 없습니다 — 추가만 됩니다. 사내망에서 열어 보는 것이 목적이면 사내망만 켜세요. 인터넷 노출은 정말 외부 공개가 필요할 때만 켭니다.

✓
세 칸을 다 채우면 배지가 «배포 대기» 로 바뀝니다. 카드마다 따로 해야 합니다.

참고 리소스 크기는 뭘 고르나
타입마다 고를 수 있는 크기가 다릅니다 — 프론트엔드는 XS 하나뿐이라 고를 것이 없습니다.

| 타입 | 고를 수 있는 크기 |
| 프론트엔드 | XS 하나뿐입니다 |
| 백엔드 | XS · S(기본) · M · L |
| DB | S 하나뿐이고 디스크는 20Gi 고정입니다 |

## 포털 07 배포하기

준비된 카드가 생기면 오른쪽 위 배포 버튼이 활성화됩니다. 첫 배포에서만 클러스터를 고르는 칸이 함께 나옵니다 — 특별한 이유가 없으면 기본으로 선택된 것을 그대로 두면 됩니다. 여기서 고른 클러스터는 이후 배포에서 다시 묻지 않습니다.

누르기 전에 카드를 한 번 확인하세요. 버튼이 열렸다고 전부 준비된 것은 아닙니다 — «배포 대기» 가 아닌 카드가 남아 있으면 그 워크로드는 이번 배포에서 제외됩니다. 누르면 앱 등록 → 동기화 요청 → 배포 상태 확인 세 단계가 돌고, 화면을 닫아도 계속됩니다.

✓
세 단계가 모두 지나가면 배포가 시작된 것입니다. 결과는 08 에서 확인합니다.

참고 배지가 어떤 순서로 바뀌나
«환경설정 필요» → «배포 대기» → «배포 중» → «정상». 중간에 «알 수 없음» 이 잠깐 지나갑니다.

| 배지 | 뜻 |
| 환경설정 필요 | 세 칸 중 안 채운 것이 있습니다 |
| 배포 대기 | 다 채웠고 아직 배포를 안 눌렀습니다 |
| 알 수 없음 | 방금 등록돼서 클러스터 상태를 아직 못 읽었습니다 |
| 배포 중 | 파드를 올리는 중입니다. 오래 머물면 앱이 뜨자마자 재시작되고 있는 것입니다 |
| 이상 | 실행은 됐지만 헬스체크를 통과하지 못했습니다 |
| 정상 | 끝입니다 |

## 08 다 됐는지 확인

### 첫 배포 완료

네 가지가 맞으면 끝입니다.

-
배포 탭의 배지가 «Synced» · «정상» «배포 중» 에서 오래 머물면 앱이 계속 죽고 있는 것일 수 있습니다

-
현재 배포 버전과 최신 빌드 버전이 같다 다르면 빌드만 되고 아직 반영되지 않은 상태입니다

-
사내망 주소로 접속된다 워크로드 카드에 링크로 떠 있습니다

-
Grafana 에서 로그가 보인다 찾을 이름은 프로젝트명과 같습니다

이후로는 `develop` 에 머지하면 배포까지 자동으로 진행됩니다. 배포 탭에 다시 올 일은 롤백 · 일시정지 · 설정 변경 정도입니다.

어딘가에서 막히면 플랫폼개발팀에 물어보세요. 프로젝트 이름, 배포 탭 화면(배지 상태가 보이게), CI 문제라면 실패한 워크플로 URL 을 함께 주면 빠릅니다.
