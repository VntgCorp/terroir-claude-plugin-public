# Terroir 안에서의 보안에 대하여

Terroir는 저장소를 만드는 순간부터 요청을 받는 순간까지 여러 단계에서 검사합니다. 대부분은 사용자가 켜지 않아도 처음부터 적용됩니다. 이 글은 각 보안 장치가 무엇을 막고 무엇은 막지 못하는지, 그래서 사용자가 직접 챙길 일은 무엇인지를 설명합니다.

R&D실 플랫폼개발팀 읽는 시간 약 5분

한눈에 보기 — 보안 장치는 두 길에 놓여 있습니다. 코드가 가는 길에서는 템플릿 · 커밋 · PR · CI · 포털이 차례로 검사하고, 요청이 오는 길에서는 인증서 · WAF · Gateway가 앱 앞을 막아섭니다. 주황색은 Terroir가 제공하는 보안 장치, 파란색은 앱이 실행되는 서버입니다.

## 결론

Terroir는 앱 바깥의 보안을 자동으로 적용합니다. 앱 안의 인증과 입력 처리는 사용자가 직접 합니다.

플랫폼이 자동으로 거는 것 — 사용자가 설정하지 않아도 처음부터 적용됩니다. 번호는 뒤에 나오는 절의 순서입니다.

## 앱 템플릿이 기본 제공하는 보안

Terroir 템플릿은 저장소 생성 시 공통 모듈을 포함합니다. 서버 앱은 이 모듈을 부르는 순간 아래 설정이 켜집니다. 화면 앱은 nginx 설정에 같은 성격의 헤더를 포함합니다.

| 설정 | 무엇을 하나 | 비고 |
| 보안 헤더 (helmet) | CSP로 스크립트 · 프레임 · 외부 리소스 출처를 제한합니다. 운영 환경에서는 HSTS를 추가합니다. | 화면 앱은 nginx가 같은 헤더 5종을 붙입니다. |
| CORS 허용 목록 | 등록한 출처에만 응답합니다. 운영 환경에서는 출처 없는 요청에 * 를 주지 않습니다. | 허용 출처는 앱이 등록합니다. |
| 요청 수 제한 | 같은 클라이언트가 1분에 100회를 넘으면 429를 반환합니다. | 항상 켜져 있습니다. WAF와 별개로 앱 안에서 동작합니다. |
| JWT 인증 가드 | @JwtProtected() 를 붙인 핸들러만 토큰을 검사합니다. | 붙이지 않은 핸들러는 열려 있습니다. |
| 입력 검증 | DTO에 없는 필드는 요청에서 버립니다(whitelist). | 모든 컨트롤러에 적용합니다. |
| 경로 차단 | /admin · /.env · /.git · /debug 같은 경로는 400으로 거부합니다. | 스캐너가 자주 시도하는 경로입니다. |
| 일반 계정 실행 | Dockerfile이 USER nodejs · USER nginx-app 으로 실행합니다. | uid 1001 |
| 환경 판정 | ENVIRONMENT 가 없으면 부팅을 거부합니다. 운영 여부를 추측하지 않습니다. | 플랫폼이 파드에 주입합니다. |

이 설정은 Terroir로 새로 만든 앱에만 있습니다. 인증 가드는 핸들러마다 붙여야 동작합니다. 빠진 핸들러가 없는지 확인해야 합니다.

## 커밋 전 검사

가장 흔한 사고는 사용자 PC에서 납니다. 테스트용 API 키를 그대로 커밋하거나 --no-verify 로 검사를 건너뛰는 경우입니다. 그래서 커밋 검사는 PC에서 돕니다.

Terroir로 새로 만든 저장소에는 git hook 세 개가 있습니다. 커밋 직전에 lint와 포맷을 맞추고 gitleaks가 비밀값을 찾습니다. 커밋 메시지는 type(scope): subject 형식만 허용합니다. push 직전에는 단위 테스트를 실행합니다. 실패하면 이유와 수정 방법을 출력합니다.

저장소에 배포한 Claude Code 차단 규칙은 hook 우회, 강제 push, 파괴 명령, 표준 파일 수정을 막습니다. 프롬프트의 키 패턴도 입력 단계에서 거부합니다.

커밋 전 검사 저장소를 만든 경로에 따라 적용 범위가 다르다
적용 부분 적용 미지원

AI 에이전트 차단 규칙새로 만든 앱 · 기존 코드를 가져온 앱 모두

기존 코드를 가져온 앱의 비밀값 검사Claude Code 커밋만 검사 · 사람이 직접 커밋하면 검사 없음

CI 단계의 비밀값 검사미지원 · PC 검사가 마지막 방어선

gitleaks가 PC에 없으면 경고만 출력하고 커밋을 허용합니다. 개발 환경 셋팅 단계에서 함께 설치합니다.

## 브랜치 보호와 PR 검사

Terroir로 저장소를 만들면 main 과 develop 에 보호 규칙을 자동 적용합니다. PR로만 코드를 반영합니다. 강제 push와 브랜치 삭제도 금지합니다. 관리자도 예외가 없습니다.

승인 수는 0이고 필수 검사도 없습니다. 목적이 리뷰 강제가 아니라 실수 방지이기 때문입니다. 혼자 운영하는 저장소도 머지할 수 있어야 합니다. 새 저장소는 CI 이력이 없어 필수 검사를 지정하면 첫 PR이 계속 대기합니다.

PR을 열면 Terroir의 공용 워크플로로 검사 다섯 개를 실행합니다. 검사 내용이 바뀌면 모든 저장소에 한 번에 반영됩니다. 표의 마지막 줄은 따로 도는 검사입니다.

| 검사 | 무엇을 보나 | 걸리면 |
| 브랜치 흐름 | feature → develop · hotfix → main · develop → main 만 허용합니다. | 검사 실패 |
| 설정 파일 형식 | terroir.json 이 스키마에 맞는지 확인합니다. | 검사 실패 |
| lint + 빌드 | 바뀐 패키지의 사내 ESLint 룰과 빌드를 확인합니다. | 검사 실패 |
| 단위 테스트 | 테스트 통과 여부를 확인합니다. | 검사 실패 |
| Docker 빌드 | 이미지 빌드 여부를 확인합니다. | 검사 실패 |
| 표준 버전 뒤처짐 | 저장소의 표준 파일이 몇 버전 뒤처졌는지 확인합니다. | patch는 경고합니다. minor 이상은 실패합니다. |

검사가 실패해도 머지할 수 있습니다. 실패를 무시한 기록은 PR에 남습니다. 누가 어떤 코드를 넣고 합쳤는지는 PR 기록으로 알 수 있고, 배포 기록은 배포를 맡은 도구 쪽에 따로 남습니다.

## 포털 로그인과 배포 권한

포털에는 회사 GitHub 조직에 속한 계정으로만 로그인할 수 있습니다. 회사 Google 계정은 조회만 가능합니다.

권한은 기본 거부입니다. 허용 목록 대신 카탈로그의 프로젝트 소유 팀(spec.owner )으로 판단합니다. 팀이나 프로젝트가 늘어도 권한 설정을 바꿀 필요가 없습니다.

Secret 값은 조회 화면에서 ******** 로 표시합니다. 암호화해 저장하므로 포털도 원래 값을 모릅니다.

포털의 권한 판정 누구인가 → 어느 팀인가 → 그 팀이 이 프로젝트의 소유 팀인가

로그인회사 GitHub 조직 멤버만 · Google 계정은 조회 전용

소속GitHub 팀을 포털 그룹으로 사용

쓰기 권한소유 팀에 속할 때만 · 배포 · 롤백 · 환경변수 변경 · DB 발급

조회전 직원 · 비밀값은 마스킹

화면과 서버는 권한을 각각 확인합니다. 화면은 권한이 없으면 버튼을 숨깁니다. 서버는 저장 요청에서 다시 확인합니다. Claude Code가 MCP로 접근할 때도 사용자 본인의 신원으로 토큰을 받으므로 같은 검사를 거칩니다.

## 외부 노출과 WAF

앱은 기본으로 비공개입니다. 배포관리 화면에서 노출을 켠 워크로드만 외부와 연결합니다. 인터넷·사내망 채널은 켜서 배포하면 잠깁니다. 되돌리려면 플랫폼개발팀에 문의해야 합니다.

사내와 사외 요청이 오는 곳에 따라 걸리는 장치가 다르다

인터넷누구나 접근 · HTTPS 자동 · WAF 적용 · {라벨}.terroir.vntgcorp.com

사내망사외접속시스템(VPN) 안에서만 · HTTPS 자동 · WAF 없음 · {라벨}-internal.…

클러스터 내부같은 클러스터의 다른 앱만 · 평문 HTTP · WAF 없음 · 앱이 호출자를 인증

인터넷에 노출하면 Terroir가 HTTPS 인증서를 발급·갱신하고, 워크로드마다 WAF(웹 방화벽, Google Cloud Armor) 정책을 연결합니다. 사내 오피스 IP는 인터넷 채널에서도 요청량 제한만 면제됩니다.

WAF는 아래 네 단계를 차례로 검사하며 요청량 제한이 마지막입니다. 앞에 두면 제한 이하의 요청이 그 자리에서 허용돼 뒤의 공격 검사를 건너뛰기 때문입니다.

WAF 평가 순서 앞에서 걸리면 거기서 끝난다 · 인터넷 채널에만 적용

① 지역한국 밖 요청 차단 · 해외 접속과 외부 웹훅은 해제 신청

② 긴급 CVELog4Shell 류 공개 취약점 패턴

③ OWASP 규칙SQL 인젝션 · XSS · 명령 주입 · 경로 탈출 · 스캐너 · 프로토콜 공격

④ 요청량 제한IP당 일정 횟수 초과분은 429 · 사내 IP는 면제

오탐이 나면 규칙을 끄지 않고 그 자리만 예외로 둡니다. Google 로그인 파라미터의 .profile 문자열이 "OS 파일 접근"으로 판정된 적이 있는데, 그 파라미터의 그 규칙만 뺐습니다. 공용 정책을 넓게 풀면 같은 정책을 쓰는 다른 앱도 그 검사를 잃기 때문입니다.

공용 WAF는 multipart 파일 업로드를 차단합니다. 파일은 브라우저가 스토리지의 서명된 URL로 직접 올립니다. 업로드 방식은 설계 단계에서 정해야 합니다. 앱이 직접 받도록 구현한 뒤에는 코드를 다시 써야 합니다.

## 실행 환경의 기본값

앱은 Google Cloud의 쿠버네티스 클러스터에서 실행됩니다. 호스트 권한을 요구하거나 서버 파일 시스템을 직접 마운트하는 컨테이너는 실행이 거부됩니다.

Terroir가 만드는 배포 설정은 실행 중 권한 상승을 막고 시스템 호출을 기본 프로필로 제한합니다. 이 값은 설정을 새로 만들 때 반영되므로, 오래된 워크로드는 설정을 다시 생성해야 적용됩니다.

CI가 이미지를 올릴 때도 키 파일이 없습니다. Google Cloud가 GitHub Actions의 일회성 신원을 직접 확인합니다. 저장소에는 클라우드 자격증명이 없습니다. Terroir가 관리하는 워크플로에서 실행할 때만 신원을 인정하므로, 그 워크플로 파일을 고치면 인증에 실패합니다.

실행 환경의 기본값 앱이 설정하지 않아도 적용되는 것

사설 노드외부 IP 없음 · 관리 엔드포인트 비공개

네임스페이스 격리프로젝트마다 분리 · 위험 컨테이너 거부

API 토큰 미주입앱이 클러스터를 조작할 수 없음

키 없는 이미지 push일회성 신원 · 지정된 워크플로만

비밀값 봉인005편 · 환경별 키로 암호화해 저장

## 사용자가 직접 챙겨야 하는 보안

플랫폼은 앱 코드가 무엇을 하는지 모릅니다. 로그인 없이 열린 API, ID를 바꿔 남의 데이터를 조회하는 요청, 취약한 라이브러리는 막지 못합니다. 확인 방법은 저장소의 terroir/docs/security/ 에 있습니다. 자주 빠뜨리는 다섯 가지입니다.

- HTTP를 HTTPS로 리다이렉트합니다. Gateway는 80 포트 요청을 그대로 앱에 전달합니다. 리다이렉트는 앱이 구현해야 합니다. 템플릿은 운영 환경에서 HSTS를 붙입니다.
- 헬스체크를 뺀 모든 핸들러에 인증을 적용합니다. WAF는 요청자를 판단하지 않습니다. 클러스터 안 다른 프로젝트의 호출도 인증해야 합니다.
- 의존성과 이미지 취약점을 점검합니다. 플랫폼 CI에는 취약점 스캔이 없고 레지스트리 자동 스캔도 꺼져 있습니다. 클러스터가 실행 중인 컨테이너의 OS 패키지를 기본 수준으로 스캔하지만 앱 라이브러리는 대상이 아닙니다. 저장소에서 Dependabot을 켜고, 릴리스 전에 이미지를 스캔합니다.
- 리뷰 승인과 필수 검사를 올립니다. GitHub 설정에서 승인 1 이상과 필수 검사를 지정합니다. 기존 코드를 가져온 저장소는 보호 규칙도 직접 만들어야 합니다.
- 일반 계정으로 실행합니다. 플랫폼은 루트 실행을 막지 않습니다. Terroir 템플릿의 Dockerfile은 일반 계정을 씁니다. 직접 쓴 Dockerfile은 확인해야 합니다.
