# onboarding

Terroir 온보딩의 진입점. 이 문서가 온보딩 전체 흐름의 source of truth다. 각 단계의 세부 절차는 해당 단계 스킬이 소유한다.

```
시작 인사 (도구를 부르기 전, 1회, 이어받기에서는 생략)
        ↓
public 마켓플레이스 자동 업데이트 설정·결과 안내
        ↓
설치된 것 소개 (1회, 이어받기에서는 생략)
        ↓
프로필 — 이메일·자신을 부를 이름
        ↓
직군·직무 질문 (직군은 기억해 두고, 여기서 분기하지 않음) → 프로필을 업무 지도에 저장 (work-map)
        ↓
공통 환경 셋팅 진행 여부 질문 (연결하기 / 건너뛰기)
        ↓ 연결하기 → env-setup   /   건너뛰기 → 바로 다음 단계
업무 지도 등록 진행 여부 질문 (등록하기 / 나중에)
        ↓ 등록하기 → work-map   /   나중에 → 바로 다음 단계
Claude 사용량 표시 설치 여부 질문 (설치하기 / 건너뛰기, 이미 설치됐거나 Claude Code 가 낮으면 묻지 않음)
        ↓ 설치하기 → terroir-statusline 플러그인 설치 · 예전 표시줄 정리   /   건너뛰기 → 바로 다음 단계
   §1-1 의 직군으로 분기 (직무를 다시 묻지 않음)
   ├─ 프로덕트 관련 직군 (개발·기획·디자인·PM 등)
   │    ├─ GitHub 계정 있음 → github-connect (조직 접근 확인, 불가면 org-access-request로 분기)
   │    │                      ↓ 완주 → §3
   │    └─ 계정 없음       → org-access-request → 대기 (승인 후 github-connect 이어받기, §3 없음)
   └─ 비 프로덕트 직군 → 바로 §3

   §3 공통 종료 출력 (완료 선언 + 시작 안내 + 커넥터 상태별 "할 수 있는 일" + 다음 발화 질문)
```

## 진행 절차

### 0-0. 시작 인사

**도구를 부르기 전에** 아래 문구를 그대로 출력한다. §0 은 명령을 여러 번 실행한 뒤에야 결과를 낸다. 인사를 먼저 내지 않으면 사용자는 설정 명령이 실행되는 동안 아무 안내도 보지 못한다.

> 반갑습니다. 지금부터 Terroir 온보딩을 시작합니다. 온보딩 단계를 마치고 나면 AI가 도구를 사용하여 업무를 도울 수 있습니다.

- 인사 다음에 곧바로 §0 을 실행한다. 인사만 내고 턴을 끝내지 않는다.
- **§4 재시작 이어받기와 §3 단독 실행에서는 내지 않는다.** §0-1 과 같은 이유다 — 이어받기는 이미 본 화면이고, §3 단독 실행은 온보딩을 마친 사람이다.

### 0. Public 마켓플레이스 자동 업데이트

이 스킬이 어떤 진입 경로로 실행되든 다른 단계보다 먼저(시작 인사를 내는 경로에서는 §0-0 다음)
`terroir-claude-plugin-public`의 사용자별 자동 업데이트를 활성화한다. 사용자에게 설정 여부를
미리 묻지 않고 설정 직후 결과를 알린다.

설정 위치는 프로젝트의 `.claude/settings.json`이 아니라 사용자 전역 설정 파일이다.
`CLAUDE_CONFIG_DIR`가 설정되어 있으면 그 디렉터리의 `settings.json`, 아니면
`~/.claude/settings.json`을 사용한다. 다음 규칙으로 `extraKnownMarketplaces`의
`terroir-claude-plugin-public` 항목을 JSON으로 병합한다.

1. `claude plugin marketplace list --json`으로 현재 등록된 마켓플레이스의 source를 확인한다.
2. 사용자 전역 설정 파일이 없으면 빈 JSON 객체로 새로 만들고, 있으면 전체 JSON을 읽는다.
3. 기존 최상위 키와 다른 마켓플레이스 항목을 모두 보존한다.
4. 해당 마켓플레이스 항목이 이미 있으면 `source`와 `ref`를 포함한 하위 값을 바꾸지 않고
   `"autoUpdate": true`만 추가하거나 갱신한다.
5. 항목이 없으면 1의 평탄화된 목록 행에서 `name`과 `installLocation`을 제외한 등록 필드를
   settings 형식의 `source` 객체로 만든 뒤 `"autoUpdate": true`를 추가한다. 예를 들어
   `{"source":"directory","path":"..."}`는
   `{"source":{"source":"directory","path":"..."},"autoUpdate":true}`가 된다.
   등록 정보를 확인하지 못했으면 임의의 source를 만들지 않는다.
6. 저장한 파일을 다시 읽어 JSON 파싱과 `autoUpdate == true`를 확인한다. 전체 파일을 고정된
   템플릿으로 덮어쓰거나 기존 main/develop/directory 채널을 바꾸지 않는다.

이번 실행에서 값을 `true`로 변경했으면 아래 한 줄을 출력하고 다음 단계로 바로 진행한다.

> ✅ `terroir-claude-plugin-public`의 자동 업데이트를 켰습니다.

이미 `true`면 아래 한 줄로 현재 상태를 알리고 다음 단계로 진행한다.

> ℹ️ `terroir-claude-plugin-public`의 자동 업데이트가 이미 켜져 있습니다.

파일 권한, 잘못된 기존 JSON, 마켓플레이스 등록 정보 누락 등으로 설정하지 못했으면 성공으로
보고하지 말고 아래처럼 안내한다. 자동 업데이트 설정 실패는 온보딩을 중단시키지 않는다.

> ⚠️ Public 플러그인 자동 업데이트를 켜지 못했습니다. `/plugin` → `Marketplaces` →
> `terroir-claude-plugin-public`에서 `Enable auto-update`를 선택해 주세요.

### 0-1. 설치된 것 소개

§0 의 자동 업데이트 결과 한 줄 다음, §1 프로필 앞에서 **한 번** 출력한다. 사용자는 위키 안내를 따라 **무엇인지 모른 채 설치 명령을 실행하고** 이 대화로 들어온다 — 직무를 묻기 전에 무엇이 깔렸고 무엇을 해 주는지 한 화면으로 보여 준다.

**아래를 그대로 출력한다.** 설명 문구는 각 플러그인의 README 와 같은 값이다 — 플러그인이 늘거나 역할이 바뀌면 이 절과 README 를 함께 고친다.

> **설치된 것** — 클로드 안에서 떼루아를 쓰게 해 주는 도구 묶음입니다.
>
> | 무엇 | 하는 일 |
> | --- | --- |
> | **terroir-onboarding** | 온보딩 진입점 — 업무 도구·GitHub 연결, 사내 플러그인 설치, 업무 지도(work-map) 등록, Claude 사용량 표시 설치까지 안내, 떼루아 개념을 물으면 레슨을 근거로 답 · 지금 이 대화 |
> | **terroir-feedback** | 떼루아를 쓰다 겪은 에러·오동작·기능 요청을 플랫폼개발팀 채널로 전송 |
> | **terroir-harness-mesh** | 평문 마크다운 지식 베이스 — 자료를 모아 두고 근거 기반으로 질의 |
>
> `terroir-feedback` · `terroir-harness-mesh` 는 온보딩과 무관하게 언제든 쓸 수 있습니다. 목록에 없으면 `/plugin` 에서 추가할 수 있습니다.
>
> 지금부터 **온보딩**을 진행합니다.

- **표는 이 절의 값을 그대로 쓴다.** §3-A 가 런타임 조회를 쓰는 것과 다르다 — 거기는 private 플러그인이 제공하는 스타트 포인트라 늘어날 수 있지만, 여기는 **이 마켓플레이스가 제공하는 것**이라 이 저장소와 함께 바뀐다.
- **플러그인 단위로만 적는다.** 온보딩 안의 skill 은 온보딩이 이어서 부르고, 따로 부를 일이 생기면(예: §3 의 `/env-setup`) 그 자리에서 안내한다 — skill 이름을 나열하면 직무를 묻기도 전에 외울 필요 없는 이름이 화면을 채운다.
- **`terroir-onboarding` 은 이 대화가 돌고 있다는 사실로 설치가 확인된다.** 나머지 둘은 함께 설치하도록 안내돼 있으나 아닐 수 있어 표 아래 한 줄로 받는다 — 설치 여부를 따로 조회하지 않는다.
- **문구가 설치 시점을 가리키지 않게 쓴다.** `/onboarding` 은 다시 실행될 수 있어 "방금 설치한" 같은 표현은 두 번째 실행에서 사실이 아니게 된다.
- **§4 재시작 이어받기로 들어온 경우에는 출력하지 않는다.** 이미 본 화면이고, 그때 필요한 것은 끊긴 지점을 잇는 것이다.
- **§3 만 단독 실행되는 경우("내가 뭘 할 수 있지?")에도 출력하지 않는다.** 그 경로는 온보딩을 이미 마친 사람이다.
- **private 플러그인 이름을 여기에 적지 않는다** — 「주의」 절의 제약을 그대로 따른다.

### 1. 프로필

채팅·메일에서 쓸 본인 이메일과 이름을 정한다. 다음 세션부터 Claude 가 업무 지도의 프로필 칸을 읽을 수 있으므로, 사용자 이름으로 메일·메시지를 쓸 때 다시 묻지 않는다.

**먼저 업무 지도를 읽는다**(`work-map` §0 의 경로). `/onboarding` 을 다시 실행한 경우처럼 프로필이 이미 있으면 있는 값은 다시 묻지 않는다.

- **네 줄(이메일 · 자신을 부를 이름 · 직무 분류 · 직무)이 모두 차 있으면** §1 과 §1-1 을 묻지 않는다. 아래 한 줄로 알린 뒤 §2 로 간다. 직무 분류는 지도의 값을 §2-3 분기에 쓴다.

  > 지난번에 저장한 프로필({자신을 부를 이름} · {직무})로 진행합니다. 바꾸려면 "지도 고쳐줘"라고 말씀해 주세요.

- **일부만 차 있으면** 빈 줄만 §1·§1-1 에서 묻는다.
- **지도가 없거나 프로필이 비어 있으면** 평소대로 묻는다.

1. 계정 정보를 읽는다.

   ```bash
   claude auth status 2>/dev/null
   grep -o '"displayName": *"[^"]*"' "${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json" 2>/dev/null | head -1
   ```

   - `email` → 이메일. 없으면(claude.ai 로그인이 아니면) 3 에서 받는다.
   - `displayName` → claude.ai 에 적어 둔 부를 이름.

2. 이름을 묻는다. displayName 이 있으면 이름 문항을 §1-1 의 두 문항과 함께 AskUserQuestion 하나에 담아 이름 → 직군 → 직무 순서로 한 번에 묻는다.

   - 이름 문항 — "채팅이나 메일에서 본인 이름을 **{displayName}**(으)로 쓸까요, 다른 이름을 쓸까요?" `(으)로` 는 이름 끝 글자에 맞춰 `로`·`으로` 중 하나로 바꿔 쓴다(받침 없음·ㄹ 받침 → `로`, 그 외 받침 → `으로`).
     - 선택지: `{displayName}` · `다른 이름 쓰기` — 다른 이름은 입력란(Other)에 적게 한다. `다른 이름 쓰기` 를 고르고 이름을 적지 않았으면 이름만 한 번 더 묻는다.
   - displayName 이 없으면 선택지를 만들 수 없으므로 "채팅이나 메일에서 쓸 본인 이름을 알려 주세요."를 일반 질문으로 묻는다.

3. 계정 정보에 이메일이 없으면 이메일도 입력으로 받는다.

### 1-1. 직군과 직무

§1 의 이름 문항과 같은 AskUserQuestion 에 담아 묻는다(이름이 이미 정해졌으면 두 문항만). 사용자가 항상 답을 아는 질문이라 부담이 없고, 이어지는 §2의 화법을 직무에 맞출 수 있다.

- **직군:** "어떤 직군에서 일하고 계신가요?"
  - `프로덕트 관련 직군` — 개발, 기획, 디자인, PM 등 프로덕트를 만드는 일
  - `비 프로덕트 직군` — 그 외 (경영지원, 영업, 인사 등)
- **직무:** "지금 맡고 있는 일은 무엇인가요?"
  - `개발` · `기획` · `디자인` · `PM`
  - 목록에 없으면 입력란(Other)에 적게 한다(예: 경영지원, 영업, 인사).

직군은 뒤의 GitHub 연결로 갈지를 가르는 두 갈래다. 선택지를 바꾸지 않는다. **여기서 바로 분기하지 않는다** — 답을 기억해 두고 §2~§2-2 를 먼저 진행한 뒤 §2-3 에서 이 답으로 분기한다.

**저장:** 답을 받으면 **저장 도구를 부르기 전에** 아래 두 줄을 먼저 출력하고, 그다음 `work-map` 스킬로 프로필 칸에 네 값(이메일 · 자신을 부를 이름 · 직무 분류 · 직무)을 한 번에 저장한다. 순서가 바뀌면 기본 권한 모드에서 설명보다 승인 창이 먼저 뜬다.

> 아래 정보로 저장합니다: {이메일} · {자신을 부를 이름} · {직무}
> 업무 지도(work-map)는 사용자 폴더(`{지도 폴더}`)에 저장됩니다. 저장 승인 창이 뜨면 허용해 주세요.

- `{지도 폴더}` 는 `work-map` §0 의 경로로 구한 실제 폴더다(`CLAUDE_CONFIG_DIR` 가 있으면 그 아래). 두 번째 줄은 `work-map` §0 의 저장 승인 안내와 같은 것이다. 여기서 냈으므로 `work-map` 은 이 세션에서 다시 내지 않는다.
- 저장에 실패하거나 사용자가 승인을 거절해도 온보딩을 멈추지 않는다 — 값은 이 세션에 기억해 두고 §2 로 간다.

### 2. 공통 환경 셋팅 (1회만)

직무와 무관하게 모두에게 필요한 도구 연결이다. AskUserQuestion으로 진행 여부를 묻되, §1-1에서 받은 직무에 맞춰 화법을 조정한다.

> 업무 도구 연결(지라·컨플루언스 / 이메일·캘린더·드라이브)을 지금 진행할까요?
> - **연결하기** — 도구 연결 상태를 점검하고 미연결 항목을 연결

#### 2-3. 단계 종료 후 직무별 분기

env-setup은 사용자가 `/mcp`를 입력하기를 기다리며 턴을 여러 번 끊는다. 그 뒤에도 **직무를 다시 묻지 않는다** — §1-1 의 직군 답을 그대로 쓰되, 분기 근거를 한 문장으로 밝히고 넘어간다 (예: "프로덕트 직군이시니 GitHub 연결로 이어가겠습니다").

- **프로덕트 관련 직군** → GitHub 계정 보유 여부를 묻는다. VNTG 조직 소속 여부는 사용자에게 묻지 않는다 — github-connect의 접근 확인이 판별한다.
  - 계정 있음 (조직 소속 여부는 몰라도 됨) → `github-connect` 스킬 실행 (계정 연결 → Git 연결 → private 플러그인 접근 확인·설치, 접근 불가면 org-access-request로 자동 분기)
  - GitHub 계정 없음 → `org-access-request` 스킬 실행 (가입 지원·접근 요청)
- **비 프로덕트 직군** → GitHub·프로덕트 도구 연결은 진행하지 않는다. 바로 §3 공통 종료 출력으로 간다.

### 3. 공통 종료 출력

온보딩을 **완주한** 경로(github-connect §6 / §2-3 비 프로덕트 분기)의 종착점. 시작 안내 스킬(`terroir-*-guide:*`)이 없는 새 세션에서 "내가 무엇을 할 수 있지?" 류의 질문을 받았을 때도 앞 단계 없이 이 섹션만 실행한다 — 그 스킬이 세션에 있으면 이 질문은 그 스킬이 받는다.

**승인 대기로 끝나는 경로(`org-access-request`)에서는 실행하지 않는다** — 온보딩이 끝난 것처럼 읽힌다.

온보딩은 이 출력에서 끝난다. **작업 방법(프로젝트 시작·개발 진행)은 온보딩이 설명하지 않는다** — 시작 단계의 스타트 포인트 스킬이 답한다. 플러그인 목록 표(`claude plugin list`)도 나열하지 않는다.

3-0 완료 선언을 먼저 내고, 아래 두 표를 순서대로 출력한 뒤, 3-C 마무리로 마친다. **화면의 마지막 줄은 언제나 "어떤 일을 해볼까요?" 질문이다** — "필요한 것이 있으면 입력하세요" 같은 별도의 입력 안내는 두지 않는다.

#### 3-0. 완료 선언 — 온보딩을 완주한 경로에서만

표에 앞서 아래 두 줄을 그대로 출력한다. §0-0 시작 인사가 "온보딩 단계를 마치고 나면 AI가 도구를 사용하여 업무를 도울 수 있습니다"라고 약속했으므로, 종착점에서 그 약속이 이뤄졌음을 같은 말로 되받는다. 둘째 줄은 뒤따르는 표가 왜 나오는지 잇는 문장이다.

> 🎉 **Terroir 온보딩을 마쳤습니다.** 이제 AI가 도구를 사용하여 업무를 도울 수 있습니다.
> 아래는 지금부터 할 수 있는 일입니다.

- **온보딩을 완주한 경로에서만 낸다** — github-connect §6 과 §2-3 비 프로덕트 분기. "내가 무엇을 할 수 있지?" 류의 질문으로 이 섹션만 단독 실행될 때는 **첫 줄을 빼고 둘째 줄만** "아래는 지금 할 수 있는 일입니다"로 바꿔 낸다. 이미 마친 사람에게 다시 마쳤다고 알리는 것은 §0-0 을 이어받기에서 생략하는 것과 같은 이유로 잡음이다.
- 이번 온보딩에서 무엇을 했는지(연결한 커넥터·설치한 도구)는 나열하지 않는다. 3-A·3-B 표가 그 상태를 이미 보여 주므로 같은 정보가 두 번 나온다.

#### 3-A. 시작 안내 — 로드된 스타트 포인트 표

세션에 로드된 스킬 중 **플러그인 이름**이 `terroir-*-guide` 패턴인 것이 **스타트 포인트**다 — 세션에는 `terroir-*-guide:<스킬>` 로 뜬다(예: `terroir-project-guide:project-guide`). 스킬 이름 자체에는 `guide` 가 없을 수 있으니 플러그인 쪽으로 판별한다. 아래 표로 안내한다 — 대상과 할 수 있는 일은 그 스킬의 description에서 뽑는다.

| 대상 | 할 수 있는 일 | 이렇게 시작하세요 |
| --- | --- | --- |
| {대상(소프트웨어·프로젝트 등)} | {그 스킬이 다루는 작업 단계를 `·`로 나열} | `/{스킬 이름}` |

**할 수 있는 일 열은 문장이 아니라 작업 단계 키워드를 `·`로 이어 쓴다** (예: `프로젝트 생성 · 기획 · 디자인 · 개발`). "~ 안내"처럼 스킬이 하는 행위를 적지 않는다 — 사용자가 찾는 것은 자기 일이 이 커맨드에 들어 있는지다.

3-B와 열 구성을 맞춘다 — 두 표가 "무엇 → 무엇을 할 수 있나 → 어떻게"로 같이 읽혀야 한다. 커맨드만 적으면 사용자는 그것을 왜 눌러야 하는지 모른다.

- **스타트 포인트 목록을 이 문서에 적어두지 않는다 — 조회 결과가 항상 진실이다.** 스타트 포인트가 늘어도 이 문서는 고치지 않고 행만 늘어난다.
- **로드된 스타트 포인트가 없으면 표를 생략하되, 그 자리를 어떻게 둘지는 설치 여부로 가른다.** 표가 비는 원인이 둘이라 화면도 둘이어야 한다 — 애초에 안 쓰는 사람과, 써야 하는데 세션에 안 잡힌 사람이다. 하나로 뭉치면 한쪽은 쓰지 않을 도구를 권유받고, 다른 한쪽은 무엇부터 하라는 말을 못 듣고 온보딩이 끝난다.

  먼저 `claude plugin list`로 설치 여부를 확인한다 — 3-B가 커넥터 연결을 런타임 확인하는 것과 같은 성격의 확인이다. 묻지 않고 알 수 있는 것을 묻지 않기 위한 순서다.

  - **설치돼 있는데 세션에 안 보인다** — 리로드가 안 먹었거나 설치됨+비활성 상태다. github-connect §5가 설치 후 `/reload-plugins`를 안내하므로 여기 도달했을 때는 보이는 것이 정상이다. **직무를 묻지 않는다** — private 플러그인은 프로덕트 직군만 설치하므로, 설치됐다는 사실이 곧 직무의 답이다.

    > ⬜ 프로젝트 시작 도구가 아직 이 세션에 보이지 않습니다.
    > 아래 안내대로 리로드해도 보이지 않으면 말씀해 주세요 — 설치 상태를 확인하겠습니다.

  - **설치 목록에도 없다** — 직무를 알아야 갈린다. §1-1 의 직군 답이 세션에 있으면 그것을 쓰고, 없으면 업무 지도 프로필 칸의 직무 분류를 쓴다. 둘 다 없으면(새 세션에서 이 섹션만 단독 실행됐고 지도도 없는 경우 — §3 첫 문단) AskUserQuestion으로 §1-1 의 직군 문항을 한 번 띄운다. **되묻는 부담보다 틀린 안내를 내는 비용이 크다** — 조건절을 붙인 한 줄("프로덕트 직군이시면 …")은 비 프로덕트 직군에게는 자기와 무관한 잡음이고, 프로덕트 직군에게는 자기를 스스로 분류하게 시키는 것이다. §1-1 도 "사용자가 항상 답을 아는 질문이라 부담이 없다"를 근거로 같은 질문을 쓴다.

    - **비 프로덕트 직군** — 표 자리를 비운다. 3-B가 그 사람이 할 수 있는 일 전부라 종료 화면이 그것으로 완결된다. 설치를 권하지 않는다.
    - **프로덕트 관련 직군** — 아직 설치 단계까지 오지 못한 것이다. 표 자리에 아래 안내를 놓는다.

      > ⬜ 프로덕트 개발 도구가 아직 설치되지 않았습니다.
      > "온보딩 시작해줘"라고 말씀하시면 GitHub 연결부터 설치까지 진행합니다.

  어느 경우든 **할 수 있는 일을 나열하지 않는다.** 목록은 스타트 포인트의 description에서 뽑는 것이고, 그것이 없어서 이 분기로 온 것이다 — 기억으로 채우면 이 문서가 사본을 갖게 된다.

#### 3-B. 할 수 있는 일 — 커넥터 상태 표

커넥터 4종의 연결 상태를 런타임 확인해(env-setup §1과 같은 방식 — 해당 서비스의 MCP 도구가 세션에 보이는지) 상태 열에 ✅(연결) / ⬜(미연결)로 표시한다.

커넥터마다 **행 3개**를 쓴다. 상태·커넥터·할 수 있는 일은 첫 행에만 적고, 나머지 두 행은 그 칸을 비운 채 예시만 채운다 — 마크다운 표 셀은 줄바꿈을 담지 못하므로 `<br>`을 쓰지 않는다.

| 상태 | 커넥터 | 할 수 있는 일 | 이렇게 말해보세요 |
| :---: | --- | --- | --- |
| ✅ 또는 ⬜ | 지라·컨플루언스 | 이슈·문서 관리 | "이번 스프린트 내 이슈 보여줘" |
| | | | "RDDP-1234 요약해줘" |
| | | | "이번 주 한 일 주간보고로 정리해줘" |
| ✅ 또는 ⬜ | 구글 메일 | 메일 검색·작성 | "안 읽은 메일 요약해줘" |
| | | | "지난주 계약 관련 메일 찾아줘" |
| | | | "이 메일 답장 초안 써줘" |
| ✅ 또는 ⬜ | 구글 캘린더 | 일정·회의실 | "내일 오후 2시 회의실 찾아줘" |

| | | | "세 명 다 되는 시간 찾아줘" |
| ✅ 또는 ⬜ | 구글 드라이브 | 자료 검색 | "작년 기획서 찾아줘" |
| | | | "이 문서 요약해줘" |
| | | | "관련 자료 모아줘" |

- **행 순서·구성은 위 표 그대로 고정한다.** 상태에 따라 정렬하거나 행을 빼지 않는다 — 볼 때마다 순서가 바뀌면 위치로 기억할 수 없고, 빠진 커넥터가 무엇인지 드러나지 않는다.
- 표 아래 안내 줄:
  - **미연결이 일부** → 미연결 커넥터를 **이름으로 불러** 안내한다. 스킬 이름(`/env-setup`)이 아니라 발화로 부른다 — 「주의」 절.

    > **구글 메일·구글 드라이브**는 아직 연결되지 않았습니다. "업무 도구 연결해줘"라고 말씀하시면 바로 연결합니다.

  - **전부 미연결** → 세 번째 열 제목을 "연결하면 할 수 있는 일"로 바꾸고, 아래로 안내한다.

    > "업무 도구 연결해줘"라고 말씀하시면 위 기능을 쓸 수 있습니다.

  - **전부 연결** → 안내 줄 없이 3-C 로 넘어간다.
- 같은 세션의 env-setup에서 연결 완료를 확인받은 항목은 도구가 안 보여도 ✅로 적되 커넥터 이름 뒤에 `*`를 붙이고, 표 아래에 "\* 방금 연결한 항목은 다음에 Claude Code를 켤 때부터 실제로 동작합니다."를 덧붙인다 — 커넥터 목록은 세션 시작 시점에 로드되기 때문이다. **이 각주는 위 세 분기와 무관하게 `*`가 하나라도 있으면 항상 붙는다.**

#### 3-C. 마무리 — 리로드와 다음 발화 질문

표와 안내 줄 다음에 아래를 놓고 화면을 끝낸다. 마지막 줄은 언제나 질문이다 — 사용자가 다음에 할 일이 "답하기"로 읽혀야 한다.

**스타트 포인트가 설치돼 있을 때** — 3-A 가 표를 냈거나 "설치됐는데 세션에 안 보임" 안내를 낸 경우. 아래 세 줄을 이 순서로 놓는다.

> 설치한 도구가 이 세션에 아직 안 보이면 `/reload-plugins` 를 입력하세요.
>
> 💬 **어떤 일을 해볼까요?** 하고 싶은 일을 편하게 적으시면 됩니다.
> 무엇을 할 수 있는지 궁금하시면 **"떼루아에서 무엇을 할 수 있지?"** 라고 물어보셔도 좋습니다.

**설치돼 있지 않을 때** — 3-A 가 "아직 설치되지 않았습니다" 안내를 냈거나 비 프로덕트 직군이라 자리를 비운 경우. 질문 한 줄만 놓는다.

> 💬 **어떤 일을 해볼까요?** 하고 싶은 일을 편하게 적으시면 됩니다.

- **질문으로 끝낸다.** "무엇을 할까요"는 답하기 어렵고, "무엇을 만들까요"는 만들기 외의 일로 온 사람을 받지 못한다. "어떤 일을 해볼까요"는 둘 다 받는다 — 바로 위 커넥터 표의 예시 발화를 그대로 적어도 답이 된다.
- **"무엇을 할 수 있는지" 줄은 설치된 화면에서만 낸다.** 그 물음을 받아줄 시작 안내 스킬은 private 플러그인이 제공한다. 그것이 세션에 없으면 그 물음을 이 섹션이 다시 받아 **같은 화면이 그대로 돌아온다** — 다음 행동을 알려주려던 안내가 사용자를 제자리에 묶는다. 비 프로덕트 직군은 private 을 설치하지 않으므로 늘 이 경우다.
- **물음 "떼루아에서 무엇을 할 수 있지?"는 글자 그대로 쓴다.** 시작 안내 스킬이 이 발화를 받도록 맞춰 둔 문구다 — 바꾸면 그 스킬이 아니라 이 스킬이 다시 받는다. 지시("물어보시면 안내해 드립니다")가 아니라 선택지("물어보셔도 좋습니다")로 둔다 — 주된 행동은 질문에 답하는 것이고 이 줄은 곁가지다.
- **리로드 줄은 조건절로 질문 앞에 둔다.** 리로드가 실제로 필요한 것은 같은 세션에서 private 플러그인을 설치한 직후(`github-connect` §5)와 3-A 의 "설치됐는데 안 보임" 분기뿐이다. 이미 스타트 포인트가 보이는 사람에게 리로드를 시키면 할 일이 없는 동작을 지시하게 된다. 질문 뒤에 두면 사용자가 마지막에 읽는 것이 질문이 아니라 명령이 된다.
- **리로드 지시는 이 줄이 단독으로 소유한다.** 3-A 의 "설치됐는데 안 보임" 분기는 상태만 알리고 리로드를 다시 지시하지 않는다 — 한 화면에 같은 지시가 두 번 나오면 어느 것을 따르라는 말인지 흐려진다.

### 4. 재시작 후 이어받기

온보딩 중 Claude Code를 재시작하면 대화가 끊겨 §1-1 의 직군 답도 사라진다. 다만 §1-1 의 저장을 마쳤다면 직무 분류는 업무 지도 프로필 칸에 남아 있다. 재시작을 안내한 스킬이 함께 알려준 재개 문구를 사용자가 입력하면 이 섹션이 받는다.

| 재개 문구 | 안내한 곳 | 이어받는 지점 |
| --- | --- | --- |
| "업무 도구 연결하고 재시작했음" | `env-setup` §3 (사용자가 재시작을 택한 경우) | 지도에 직무 분류가 있으면 그것을 쓰고, 없으면 §1 프로필부터 다시 진행 |
| "git 설치하고 재시작했음" | `github-connect` §1 (Windows git·gh 설치) | 직무를 묻지 않고 `github-connect` §1로 |

- **"업무 도구 연결하고 재시작했음"** → §1 처음의 "먼저 업무 지도를 읽는다" 규칙대로 프로필에 있는 값은 묻지 않고, 빈 줄만 §1·§1-1 에서 묻는다. 직무 분류가 지도에 있으면 그것을 §2-3 분기에 쓴다. 그다음 §2는 진행 여부를 묻지 말고 `env-setup`을 바로 실행하고, 이어서 §2-1 로 간다. env-setup §1이 상태를 확인해 이미 연결된 항목은 건너뛴다. 지도에 직무 분류가 없는 경우에 한해 §2-3의 "직무를 다시 묻지 않는다"가 적용되지 않는다(§1-1 에서 다시 물었으므로 그 답을 쓴다).
- **"git 설치하고 재시작했음"** → 이 문구는 프로덕트 직군이 확정된 뒤에만 나오므로 직무·환경 셋팅을 다시 묻지 않고 `github-connect` §1로 바로 넘긴다.

## 주의

- 이 스킬과 플러그인 문서에는 사내 URL·사내 이메일·private 플러그인의 이름 목록을 적지 않는다. 사용자 안내에 필요한 스타트 포인트 목록은 §3-A처럼 런타임 조회로 얻는다.
- **사용자에게 보여 주는 문장에서는 스킬을 이름이 아니라 하는 일로 부른다.** 인용 블록·AskUserQuestion 선택지·"…라고 알린다" 예문이 대상이다. 스킬 이름(`env-setup`·`dev-env-setup` 등)은 사용자가 외울 필요 없는 식별자라 그대로 말하면 무엇인지 모른다. 자연어로 발동되는 스킬은 그 스킬의 `when_to_use` 트리거를 그대로 써서 "…라고 말씀하세요"로 안내한다 — 그 말로 그 스킬이 뜨는 것이 보장되고 문구의 출처가 한 곳이 된다. 명령 병기는 사용자가 칠 명령을 문서로 나열하는 곳(README·lessons)에서만 하고, 그때도 하는 일 뒤에 괄호로 둔다(예: `개발 환경 셋팅 (/dev-env-setup)`). `plugin:skill` 전체 표기는 쓰지 않는다. 내장 명령(`/reload-plugins`·`/plugin`·`/mcp`)은 대체 표현이 없으니 그대로 쓴다. 스킬 본문이 다른 스킬을 가리키는 지시문(Claude 가 읽는 문장)은 이 규칙의 대상이 아니다.
