# 리포트 템플릿

리포트는 두 형태로 존재한다. **미리보기(텍스트)** 는 사용자가 AskUserQuestion 에서 보는 것이고, **report.json** 은 `send.sh` 가 카드로 바꿔 보내는 것이다. 항목은 1:1 이다 — 미리보기에서 승인한 값만 JSON 에 넣는다.

`{ }` 자리를 채운다. 빈칸을 비워 두지 않는다 — 모르면 사용자에게 **그 항목만** 묻는다.

## 분류 넷

| 이모지 | 라벨 | `category` | 무엇을 받나 |
|---|---|---|---|
| 🐞 | 에러·오동작 | `error` | 진행하다 문제가 생긴 모든 것. 오류 문구가 없어도 결과가 잘못됐으면 여기다 |
| 💡 | 기능 요청 | `feature_request` | 없는 기능, 그리고 있는 기능의 불편. 둘을 한 분류로 받는다 |
| 🔑 | 권한 요청 | `access_request` | 진행하다 권한·접근이 막혀 생긴 모든 것 |
| 💬 | 기타 | `other` | 위 셋 어디에도 넣을 수 없는 것 |

### 분류를 고르는 순서

위에서부터 판별한다. 앞에서 걸리면 뒤를 보지 않는다.

1. 권한·접근이 막혀서 멈췄나 → `access_request`
2. 하려던 것이 애초에 없어서 못 했나, 또는 되지만 불편한가 → `feature_request`
3. 진행하다 실패했거나 결과가 잘못됐나 → `error`
4. 셋 다 아니다 → `other`

`other` 는 마지막 수단이다. **자동 제안(triggers.md) 경로에서는 `other` 를 고르지 않는다** — 트리거가 이미 상황을 알고 있으므로 앞의 셋 중 하나로 정해진다. `other` 는 사용자가 직접 `/feedback` 을 부른 경우에만 쓴다.

분류 질문의 선택지는 **넷이 아니라 셋**이다. `other` 를 선택지로 만들지 않는다 — AskUserQuestion 이 "Other" 항목을 자동으로 붙이며, 사용자가 그것을 고르면 입력한 텍스트를 `content` 로 삼아 `other` 로 기록한다.

## 미리보기 — 🐞 에러·오동작

```
🐞 [에러·오동작] {한 줄 제목}

발생한 위치
  {스킬} · {맵 단계}
기대한 동작
  {안내나 문서대로면 이렇게 되어야 한다 — 1~2문장}
실제 동작
  {실제로 일어난 일. 오류 문구가 있으면 요약하지 않고 그대로}
재현 순서
  1. {첫 행동}
  2. {다음 행동}
  3. {결과가 나온 지점}
추정 원인
  {떼루아 어느 파일·화면의 무엇이 문제인지. 확인한 근거를 함께}
해결방안
  {팀이 무엇을 무엇으로 바꾸면 되는지}

신고 {이메일} · 환경 {collect-env.sh 출력}
```

## report.json

```json
{
  "category": "error | feature_request | access_request | other",
  "title": "증상 한 줄 — 분류·스킬 이름은 넣지 않는다",
  "skill": "deploy-config",
  "stage": "5 DEPLOYMENT",

  "expected": "…", "actual": "…", "repro": ["…", "…"], "cause": "…", "fix": "…",
  "want": "…", "now": "…",
  "tried": "…", "blocked": "…", "need": "…",
  "content": "…",

  "reporter": "user@vntgcorp.com",
  "env": "private 8b8a07e (8) · public 20523f7 (2) · Claude Code 2.1.250 · macOS (arm64)"
}
```

분류마다 쓰는 필드가 다르다. 해당 분류의 필드만 넣는다.

| `category` | 본문 필드 |
|---|---|
| `error` | `expected` · `actual` · `repro[]` · `cause` · `fix` |
| `feature_request` | `want` · `now` |
| `access_request` | `tried` · `blocked` · `cause` · `need` |
| `other` | `content` |

`cause` 는 `error` 와 `access_request` 가 공용으로 쓴다. 리포트 ID 는 `send.sh` 가 만들어 카드에 넣으므로 JSON 에 넣지 않는다.

`send.sh` 가 만드는 것이 둘 더 있다.

- **카드 제목** — `{이모지} [{분류}] {title}` 로 조립한다. `title` 에 이모지나 분류를 넣지 않는다
- **본문 첫 항목** — `skill` 과 `stage` 를 ` · ` 로 이어 넣는다. 라벨은 분류에 따라 갈린다 — 「발생한 위치」 또는 「대상」. 아래 「본문 첫 항목」 절을 따른다

## 채우기 규칙 — 공통

| 항목 | 규칙 |
|---|---|
| 제목 | 증상만. "배포 롤백 안내 없음" ○ / "deploy-config: 배포 롤백 안내 없음" ✕ / "동작하지 않음" ✕. 이모지·분류는 `send.sh` 가 붙이므로 넣지 않는다 |
| 이메일 | `git config user.email`. 없으면 묻는다 |
| 길이 | 항목마다 3문장 이내. 로그가 길면 핵심 줄만 |

## 채우기 규칙 — 본문 첫 항목 (`skill` · `stage`)

본문 첫 항목은 `skill` 과 `stage` 를 ` · ` 로 이은 것이다. **라벨과 값의 의미가 분류에 따라 갈린다.**

| 분류 | 라벨 | `skill` 에 무엇을 적나 |
|---|---|---|
| `error` | 발생한 위치 | 문제가 난 스킬 — 실행 중이던 것 |
| `access_request` | 발생한 위치 | 막힌 지점의 스킬 |
| `feature_request` | 대상 | 요청이 붙을 스킬 |
| `other` | 대상 | 관련 스킬. 대개 빈다 |

스킬이 없으면 플러그인 이름을 적는다. `stage` 는 `1 KICKOFF` ~ `6 OBSERVABILITY` 또는 `0 SETUP` 중 하나이고, 단계와 무관하면 비운다.

**기능 요청은 스킬을 추측으로 채우지 않는다.** 직전에 돌던 스킬을 집어넣으면 팀이 엉뚱한 담당에게 배정한다.

- 요청이 붙을 자리가 분명하면 스킬과 단계를 모두 적는다
- 스킬은 정해지지 않고 단계만 정해지면 스킬을 비우고 단계만 적는다 — 단계만 있어도 담당이 정해진다
- 둘 다 정해지지 않으면 둘 다 비운다. 항목이 나타나지 않으며, 떼루아 전반에 대한 요청은 그것이 정상이다

## 채우기 규칙 — 「추정 원인」과 「해결방안」

**이 두 항목의 독자는 플랫폼 개발팀이다.** 떼루아를 만드는 사람들이 그대로 열어 보고 고칠 수 있게 쓴다. 사용자에게 설명하는 문장으로 쓰지 않는다.

「추정 원인」

- 레포 이름 + 레포 기준 파일 경로 + 행 번호를 적는다. 스킬 이름만 적지 않는다
- 재현 조건을 적는다 — OS · 런타임 버전 · 사내망 여부. 다른 조건에서 통과했으면 그것도 적는다
- 포털·사내 표준 문제면 경로 대신 화면 주소나 관리 파일명을 적는다
- 확인 범위를 밝힌다. 파일을 열어 보았는지, 로그만 보았는지
- 라벨이 이미 「추정」이므로 값 안에 `추정 —` 을 덧붙이지 않는다

「해결방안」

- 무엇을 무엇으로 바꾸는지 문자열 단위로 적는다
- 대안이 있으면 하나를 권하고 그 이유를 한 줄 적는다
- 검증했으면 무엇까지 확인했는지 적는다
- **사용자 우회가 아니라 떼루아 변경을 적는다.** 우회는 이미 사용자가 했거나 하지 못했다

**아무 근거도 없으면 `확인하지 못함` 이라고 적는다.** 빈칸으로 두지 않는다 — 빈칸은 "적지 않았다"와 "찾지 못했다"가 구분되지 않는다. `확인하지 못함` 이 적혀 있으면 팀은 Claude 도 찾지 못했다는 사실을 정보로 받는다.

`access_request` 의 「추정 원인」은 어느 계층 권한이 빠졌는지를 짚는다. 조치가 갈린다.

| 짚은 원인 | 팀이 할 일 |
|---|---|
| 조직 멤버가 아니다 | 조직 초대 |
| 조직에는 있으나 팀에 없다 | 팀 추가 |
| 팀에는 있으나 이 프로젝트만 빠졌다 | 프로젝트 권한 부여 |
| 역할이 조회 전용으로만 부여됐다 | 역할 승격 |

## 채우기 규칙 — 분류별

| 항목 | 규칙 |
|---|---|
| 실제 동작 | 오류 문구는 그대로 넣는다. 팀이 검색할 수 있어야 한다. 문구가 없으면 화면에서 본 것을 적고 문구가 없었다는 사실도 적는다 |
| 재현 순서 | 사용자가 실제로 한 순서. 추측으로 채우지 않는다. 항목 하나가 한 행동 |
| 현재 방식 | 없는 기능이면 "하지 못한다" 또는 우회 방법. 우회할 방법이 없으면 "우회할 방법이 없다"고 적는다. 있는 기능의 개선이면 지금 어떻게 동작하는지 적는다 |
| 막힌 화면·문구 | 화면 이름과 화면에 뜬 문구를 함께 적는다. 메뉴 자체가 보이지 않았다면 그 사실을 적는다 |
| 요청 권한·대상 | **세 줄을 모두 채운다.** 누구 · 무엇에 · 어떤 권한 |
| 내용 | 형식을 규정하지 않는다. 전달할 내용을 그대로 적는다 |

### 「누구」는 반드시 확인한다

신고자 이메일을 자동으로 넣지 않는다. 권한이 필요한 사람이 신고자와 다를 수 있다.

- 본인만 필요한가 → 이메일
- 팀 전체가 필요한가 → 팀 이름
- 다른 사람 몫으로 요청하는가 → 그 사람의 이메일

「무엇에」는 서술이 아니라 식별자로 적는다 — "배포 화면" ✕ / "떼루아 프로젝트 order-api · dev 환경" ○.

「어떤 권한」은 화면에 보인 역할 이름이 있으면 그 이름을 그대로 적는다.

## 넣지 않는 것

- 대화 전체
- 사용자 프로젝트의 소스코드 · 파일 내용 · 고객 데이터
- 토큰 · 비밀번호 · API 키 · webhook URL 등 자격증명

**떼루아 파일은 예외다.** 「추정 원인」과 「해결방안」이 성립하려면 문제가 있는 자리를 지목해야 한다.

| 넣어도 된다 | 넣지 않는다 |
|---|---|
| 떼루아 파일(플러그인 스킬 · 사내 표준 관리 파일)의 해당 한두 줄 | 사용자 프로젝트의 코드 |
| 그 파일의 레포 · 경로 · 행 번호 | 파일 전체나 긴 블록 |
| 명령어 · 설정값 | 자격증명이 담긴 줄 |

떼루아 파일은 플랫폼 개발팀 소유라 인용이 곧 참조다. 사용자 프로젝트 코드는 애초에 이 채널의 대상이 아니다.

전송 전 미리보기에서 사용자가 위 항목이 섞였는지 확인한다. 이것이 승인 단계의 목적이다.
