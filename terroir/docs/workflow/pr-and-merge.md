## 규칙 요약

1. PR은 **작게** — 리뷰어가 한 번에 이해할 수 있는 단위로 쪼갠다.
2. PR 안에서는 자유롭게 여러 번 커밋한다. 커밋 정리는 머지 시점에 한다.
3. `feature → develop` 머지는 **squash merge** — 기능 하나가 커밋 하나로 남는다.
4. 큰 작업은 **에픽 브랜치**를 만들고, 그 위에 작은 task PR을 쌓은 뒤 마지막에 에픽을 develop으로 머지한다.
5. 롤백은 두 층위: **코드 롤백**(git revert)과 **배포 롤백**(ArgoCD 이전 이미지) — 상황에 맞게 선택.

## 왜 squash인가 — 복원 가능성

머지 방식의 기준은 "히스토리가 예쁜가"가 아니라 **"문제가 생겼을 때 얼마나 쉽게 되돌리는가"**입니다.

```
squash 머지 후 develop:
  ● feat(orders): add order cancel (#41)     ← 기능 = 커밋 1개
  ● feat(auth): add social login (#40)
  ● fix(api): pagination total count (#39)

기능 #40에 문제 발견 → git revert 한 방으로 기능이 통째로 빠진다.
```

- 작업 중의 커밋("wip", "fix typo", "리뷰 반영")이 develop에 섞여 있으면,
  롤백할 때 **어디부터 어디까지가 그 기능인지** 찾는 것부터 일이 됩니다.
- squash로 "1 기능 = 1 커밋"이 되면 기능 단위로 넣었다 뺐다 할 수 있습니다.
- 기능의 **일부만** 살리고 싶다면: revert 후 필요한 부분만 cherry-pick하거나,
  커밋을 정리해 다시 머지합니다.

## 기본 흐름 (일반 크기 작업)

```
develop ──┬─ feature/add-cancel ── 커밋 n개 ── PR ──[squash]──▶ develop (1 커밋)
          └─ feature/fix-total  ── 커밋 n개 ── PR ──[squash]──▶ develop (1 커밋)
```

- PR 제목은 커밋 컨벤션과 같은 형식으로: `feat(orders): add order cancel`.
  squash 커밋 메시지가 PR 제목에서 만들어지기 때문입니다.
- PR 본문에는 무엇을/왜/영향 범위를 적습니다. 리뷰어와 6개월 뒤의 자신이 독자입니다.

### PR 본문에 담을 것

```markdown
## 요약
무엇을 왜 바꿨는지 2~3줄.

## 구현
접근 방식, 고민했던 대안이 있으면 왜 이 쪽을 택했는지.

## 테스트
어떤 테스트를 추가/수행했는지. 재현·확인 방법.

## 영향 범위
영향받는 모듈/API/스키마. 마이그레이션이 있으면 명시.
관련 티켓: (있으면 티켓 번호)
```

- 화면 변경이면 스크린샷(전/후), API 변경이면 요청/응답 예를 붙이면 리뷰가 빨라집니다.
- 보안·데이터에 영향 있는 변경(권한, 마이그레이션, 민감정보 취급)은 본문에 **명시적으로 강조**하세요.
- PR 제목이 이미 `type(scope)`를 담으므로 본문에 타입을 중복 표기하지 않습니다. repo PR 템플릿도 이 골격을 표준으로 삼습니다.

## 리뷰

리뷰는 **채점·통과 도장이 아니라 두 가지를 위한 협업**입니다.
- **공유** — 작성자가 무엇을·왜 했는지 팀이 알게 되고, 리뷰어가 그 위에서 대응·후속 작업을 이어갈 수 있게 한다.
- **품질** — 지금 넣는 변경이 나중에 비용이 되지 않게 함께 점검한다.

**"동작하니까 OK"로 끝내지 않습니다.** 가장 흔한 실패 모드가 "돌아가면 통과"인데, 동작은 **최소 기준**일 뿐입니다 — 돌아가도 구조·설계가 나쁘면 다음 변경의 발목을 잡으므로 그때 짚습니다.

**함께 보는 것** (어느 하나도 "동작하니까"로 건너뛰지 않기):
- **동작** — 요구사항 충족, 경계 조건, 에러 경로.
- **보안** — 소유권 검사 누락, 입력 검증 누락, 민감정보 노출 ([security-checklist.md](../api/security-checklist.md)).
- **구조·설계** — 레이어·경계·네이밍·응답 포맷 등 가이드 컨벤션. 지금 동작해도 구조가 나쁘면 여기서 잡는다(포맷 자체는 도구 소관이라 지적하지 않음).
- **테스트** — 핵심 로직에 테스트가 함께 왔는가, 테스트가 계약을 검증하는가.

리뷰 문화:

- 피드백은 **코드에 대해, 구체적으로**. "이상해요"가 아니라 "X 케이스에서 null이 들어오면 여기서 터질 것 같아요".
- 제안과 필수를 구분해서 표시: `[필수]` 머지 전 반영 / `[제안]` 판단에 맡김.
- **응답은 빠르게 — 당일 내 첫 반응, 늦어도 다음 영업일 오전.** 바로 리뷰가 어려우면 언제 가능한지라도 남기세요.
  PR이 오래 열려 있을수록 충돌·드리프트 비용이 커집니다.
- 자기 승인(self-approve) 금지. AI가 작성한 코드도 **사람 리뷰를 동일하게** 거칩니다.

### 승인 수 — 강제하지 않는다, 단 직접 푸시는 금지

- **`develop`·`main`에 직접 push하지 않습니다. 모든 변경은 PR을 경유합니다.** 이 하나가 지켜야 할 규칙이고, repo에 branch protection이 설정돼 있으면 그게 강제합니다(새 repo는 protection을 켜 두세요).
- **승인 인원 수는 고정하지 않습니다.** 숫자를 강제하면 리뷰어 부재가 곧 머지 블로커가 됩니다.
  팀과 작업의 성격에 맞게 정하세요:
  - 일반적인 변경 — 승인 1명이면 충분합니다.
  - 리스크가 크거나 **공유가 필요한** 변경(보안/인증, DB 마이그레이션, 공통 라이브러리, 여러 팀에 영향 주는 것 등)은
    리뷰어를 늘리는 것을 권장합니다. 어떤 변경이 그에 해당하는지도 팀이 정합니다.

## 큰 작업 — 에픽 브랜치

리뷰 가능한 크기로 쪼갤 수 없는 큰 작업(여러 도메인에 걸친 기능, 대규모 리팩토링)은
develop에 직접 쌓지 말고 에픽 브랜치를 경유합니다.

```
develop ── epic/order-v2 ──┬─ feature/cancel-api   ── PR ──[squash]──▶ epic/order-v2
                           ├─ feature/refund-flow  ── PR ──[squash]──▶ epic/order-v2
                           ├─ feature/cancel-ui    ── PR ──[squash]──▶ epic/order-v2
                           └──────────── 완성 후 PR ──[merge commit]──▶ develop
```

- **task PR → 에픽: squash.** 리뷰 단위가 작아지고, 에픽 브랜치에 task별 커밋이 깔끔하게 쌓입니다.
- **에픽 → develop: merge commit.** 에픽 전체를 다시 squash하면 수천 줄짜리 커밋 하나가 되어
  task 단위 추적이 사라집니다. merge commit이면 에픽 통째 revert(`git revert -m 1`)와
  task 단위 추적이 둘 다 가능합니다.
- 에픽 브랜치는 주기적으로 develop을 받아(머지) 드리프트를 줄이세요.

## 롤백 — 두 층위를 구분하라

GitOps 환경에서는 "코드를 되돌리는 것"과 "배포를 되돌리는 것"이 다른 동작입니다.

| 층위 | 방법 | 언제 |
|------|------|------|
| **배포 롤백** | ArgoCD에서 이전 revision/이미지로 전환 (IDP 배포 관리 화면) | 장애 상황. 지금 당장 서비스를 이전 상태로 |
| **코드 롤백** | `git revert <squash 커밋>` → PR → 머지 → 재배포 | 원인 커밋을 히스토리에서 정식으로 제거 |

장애 시엔 **배포 롤백이 먼저**입니다(빠름). 코드 롤백은 그 후 차분히.
배포 롤백만 하고 코드 롤백을 잊으면 다음 배포에서 문제가 다시 나갑니다 — 둘은 세트입니다.

## Do / Don't

```
✅ Do
- PR 하나 = 리뷰 가능한 한 가지 주제
- PR 안에서는 편하게 커밋 (어차피 squash됨)
- PR 제목을 컨벤션 형식으로 (squash 커밋 메시지가 됨)
- 에픽 → develop 은 merge commit

❌ Don't
- 여러 기능을 한 PR에 (리뷰 불가 + revert 단위 붕괴)
- 에픽 → develop 을 다시 squash (task 추적 소실)
- develop에 직접 push (PR 없이) — protection이 설정돼 있으면 막힌다. 없더라도 하지 말 것
- "리뷰 다 달렸으니" rebase --force로 히스토리 재작성 후 강제 푸시 (리뷰 맥락 파괴)
```

## 근거

- squash 머지: GitHub "squash and merge" 표준 관행 — 선형 히스토리 + 기능 단위 revert
- 작은 PR: [Google Engineering Practices "Small CLs"](https://google.github.io/eng-practices/review/developer/small-cls.html) — 작은 변경이 리뷰 속도·결함율 모두 우수
- 짧은 브랜치·작은 배치: DORA(Accelerate) 고성능 조직 패턴
- 배포 롤백: ArgoCD revision 롤백 — [ci-cd.md](ci-cd.md) 배포 흐름 참고
