# 소프트웨어 종류 (spec.type)

> Managed by gh-terroir-greenfield. 사내 표준 변경 시 자동 갱신됩니다. 직접 수정하지 마세요.

카탈로그에 올리는 모든 소프트웨어는 **종류를 하나** 갖습니다. `catalog-info.yaml` 의
`spec.type` 이 그 값이고, 만들 때 고릅니다. 종류는 목록에서 무엇을 찾는지의 기준이 되고,
엔티티 화면에 어떤 도구가 붙는지를 정합니다.

이 문서는 사람과 AI 어시스턴트가 **같은 기준으로 종류를 고르도록** 하기 위한 것입니다.

## 규칙 요약

| 종류 | 한 문장 정의 | 판별 질문 | 사내 예 |
|------|-------------|----------|---------|
| `service` | 실행되어 요청을 처리하는 백엔드 | 떠 있으면서 무언가를 처리하는가 | `terroir-kmm` · `RND-IDP` · `terroir-file-service` |
| `library` | 다른 소프트웨어가 가져다 쓰는 코드 | 남의 코드가 이것에 의존하는가 | `terroir-sdk` · `terroir-reusable-workflow` |
| `tool` | 사람이 실행하는 도구 | 개발자가 직접 돌리는가 | `gh-terroir-greenfield` · `terroir-e2e` · `terroir-claude-plugin` |
| `documentation` | 문서가 산출물인 사이트 | 코드가 아니라 글이 결과물인가 | (현재 사내 사례 없음) |
| `infrastructure` | 인프라·배포 선언이 산출물인 저장소 | 실행되는 것이 아니라 무엇을 띄울지 적은 것인가 | `RND-INFRA` · `terroir-manifests` · `terroir-kubespray` |

## 종류는 만들 때 고르고, 바꿀 수 없습니다

종류는 **불변**입니다. 값을 나중에 고쳐 쓰지 않습니다.

종류에 따라 붙는 화면과 도구가 달라지므로, 값이 도중에 바뀌면 그 소프트웨어를 참조하던
쪽의 전제가 조용히 깨집니다. 그래서 이름·프로젝트 소속과 함께 엔티티의 정체성을 이루는
값으로 다룹니다.

**잘못 골랐다면** 값을 고치는 대신 올바른 종류로 엔티티를 새로 만들고, 기존 엔티티는
`spec.lifecycle` 을 `deprecated` 로 바꿔 둡니다. 성숙도는 반대로 **바뀌는 값**이라 언제든
올리고 내릴 수 있습니다.

## 각 종류

### `service` — 실행되어 요청을 처리하는 백엔드

떠 있는 상태로 요청을 받아 처리합니다. HTTP API 를 제공하는 것이 가장 흔하지만, 메시지를
소비하는 워커도 여기 해당합니다.

- **사내 예** — `terroir-kmm`(매니페스트 관리 API), `RND-IDP`(개발자 포털),
  `terroir-file-service`·`terroir-notification-service`(공통 서비스)
- **반례** — 프런트엔드 코드가 함께 있다고 종류가 달라지지 않습니다. `RND-IDP` 는 백엔드와
  화면이 한 레포에 있지만 `service` 입니다. 배포 단위가 하나이기 때문입니다.
- **한 애플리케이션에 워크로드가 여럿이어도 `service` 하나**입니다. `terroir-sample-project` 는
  `apps/` 아래 백엔드 둘·프런트 하나를 갖지만 카탈로그 엔티티는 하나입니다. 워크로드는
  카탈로그가 아니라 배포관리가 다룹니다.

### `library` — 다른 소프트웨어가 가져다 쓰는 코드

직접 실행하지 않고, 다른 소프트웨어가 의존해서 씁니다. 판별의 핵심은 **"남의 코드가 이것을
불러 쓰는가"** 입니다.

- **사내 예** — `terroir-sdk`(다른 앱이 install 해서 씀),
  `terroir-reusable-workflow`(다른 레포가 `uses:` 로 참조함)
- **반례** — `gh-terroir-greenfield` 는 코드가 있지만 라이브러리가 아닙니다. 사람이 명령으로
  실행하는 것이지 남의 코드가 의존하는 것이 아니라서 `tool` 입니다.

### `tool` — 사람이 실행하는 도구

개발자가 직접 돌립니다. 실행 가능한 산출물이 있지만 서버로 떠 있지 않고, 다른 코드가
의존하지도 않습니다.

- **사내 예** — `gh-terroir-greenfield`·`gh-terroir-byor`(gh CLI 확장),
  `terroir-e2e`(e2e 하네스), `terroir-claude-plugin`(Claude Code 플러그인)
- **반례** — 서버로 떠서 요청을 받으면 `tool` 이 아니라 `service` 입니다.
- **왜 `library` 로 뭉치지 않는가** — 목록에서 "가져다 쓸 것" 과 "실행할 것" 이 섞이면
  무엇을 기대해야 할지 판단할 수 없게 됩니다.

### `documentation` — 문서가 산출물인 사이트

코드가 아니라 글이 결과물입니다. `docs/` 와 `mkdocs.yml` 을 두고 Backstage 의 Docs 탭으로
발행합니다. 이 구조는 Backstage 공식 문서가 독립 문서 컴포넌트에 권장하는 형태 그대로입니다.

- **사내 예** — 현재 없습니다. 사내 문서는 대부분 코드 레포 안에 함께 있습니다.
- **반례** — 코드 레포에 문서가 있다고 `documentation` 이 되지 않습니다. 그 경우는 원래
  종류를 유지하고 `backstage.io/techdocs-ref` 애노테이션으로 문서를 발행합니다.
  **문서 발행과 종류는 별개입니다** — 어떤 종류든 문서를 발행할 수 있습니다.

### `infrastructure` — 인프라·배포 선언이 산출물인 저장소

실행되는 소프트웨어가 아니라 **무엇을 어떻게 띄울지 적어 둔 선언**이 산출물입니다.
Terraform·Kubernetes 매니페스트·ArgoCD 설정처럼, 도구가 읽어서 실제 자원을 만드는 파일들입니다.

- **사내 예** — `RND-INFRA`(Terraform·Kubernetes·ArgoCD 선언),
  `terroir-manifests`(배포 매니페스트), `terroir-kubespray`(클러스터 프로비저닝)
- **성격이 둘로 갈립니다** — `RND-INFRA` 는 사람이 PR 로 고치는 코드이고,
  `terroir-manifests` 는 배포관리 도구가 생성·관리하는 산출물이라 **사람이 직접 손대면
  안 됩니다.** 지금은 한 종류로 묶여 있으니 레포의 README 를 먼저 확인하세요.
- **반례** — 애플리케이션 레포 안의 `infra/` 디렉터리나 `terroir.json` 은 해당하지 않습니다.
  그건 그 애플리케이션의 일부입니다.

## 배포 여부는 종류가 아닙니다

**"배포되는가" 로 종류를 고르지 마세요.** 종류는 그 소프트웨어가 *무엇인가*를 말하고,
배포는 지금 그것이 *어떻게 운영되는가*의 사실입니다. 두 축은 따로 움직입니다.

- `terroir-kmm` 과 `RND-IDP` 는 실제로 배포되어 떠 있지만 배포관리(KMM) 에 등록돼 있지
  않습니다. 인프라 저장소의 Helm 차트로 직접 배포되기 때문입니다. 그래도 종류는 `service`
  입니다 — 하는 일이 백엔드 서비스이기 때문입니다.
- 배포 대상 여부의 **진실 공급원은 `terroir-manifests` 하나**입니다. 거기에 배포 자산이
  있으면 배포 대상이고 없으면 아닙니다. 카탈로그 기술서의 배포 연결 애노테이션은 "배포를
  어디에 물어볼지" 를 담은 **조회 키**이지 배포 여부 표시가 아니라서, 종류와 무관하게 항상
  심습니다.
- 그래서 엔티티 화면에 배포 정보가 "등록되지 않음" 으로 나오는 것은 **정상 상태**입니다.
  고장이 아닙니다.

같은 이유로 배포 여부를 종류로 나누지 않습니다. 배포 여부는 바뀌는 사실인데 종류는 불변이라,
나중에 배포관리로 옮겨 오는 순간 엔티티를 교체해야 하기 때문입니다.

## 어느 것에도 맞지 않을 때

먼저 **억지로 맞추지 말고** 플랫폼 개발팀에 문의하세요. 애매한 것을 기존 종류에 밀어 넣으면
종류를 기준으로 한 판단이 전부 흐려집니다.

새 종류는 아래 셋에 답할 수 있을 때 더합니다.

- **배포 대상인가.** 엔티티 화면에 배포 정보를 붙일지가 여기서 갈립니다.
- **기존 종류로 뭉뚱그리면 무엇을 잃는가.** 잃는 것을 말할 수 없으면 기존 종류로 충분합니다.
- **그 종류에만 붙일 화면이나 도구가 있거나, 붙일 계획이 있는가.**

값을 더하는 일 자체는 위험이 작습니다. Backstage 공식 문서도 새 종류를 더하는 것은 노력과
위험이 작다고 하면서, 대신 **맞지 않는 것을 모아 담는 `Other` 같은 종류는 만들지 말라**고
권합니다. 종류가 구체적일수록 그 종류에 맞는 도구를 붙이기 쉽기 때문입니다.

## 근거

- Backstage 서술자 형식 — <https://backstage.io/docs/features/software-catalog/descriptor-format/>
  (`Component` 의 정의와 `spec.type` 의 well-known 값 `service`·`website`·`library`)
- Backstage 모델 확장 — <https://backstage.io/docs/features/software-catalog/extending-the-model>
  (새 종류 추가의 위험도, catch-all 을 권하지 않는 이유, 종류가 구체적일수록 맥락 도구를
  붙이기 쉽다는 지침)
- Backstage 문서 발행 — <https://backstage.io/docs/features/techdocs/creating-and-publishing/>
  (독립 문서 컴포넌트에 `spec.type: documentation` 을 쓰는 공식 예시)
- 사내 결정 근거는 플랫폼 개발팀이 관리하는 ADR 에 있습니다. 종류 분류와 값의 변경 경계,
  배포 대상 여부의 진실 공급원, 카탈로그와 배포관리의 역할 경계가 거기에 정리돼 있습니다.
  접근 권한에 따라 열리지 않을 수 있으며, 이 문서만으로 판단할 수 있게 쓰여 있습니다.
